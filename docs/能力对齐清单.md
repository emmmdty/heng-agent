## 二、本轮补齐的 8 项（实现要点与验证）

### 1. Hook Pipeline（能力清单第 1 项）

**取舍**：基线参考设计的 `@harness_hook` 自建 registry 会与既有 `ToolResilienceMiddleware`
（AgentScope 2.0 原生 `ToolMiddlewareBase` 洋葱拦截）重复造轮子，带来两套执行顺序与异常语义。
改用框架原生机制：`on_tool_call` 内 `next_handler` 前后天然对应 `pre_tool_call` / `post_tool_call`。

洋葱顺序 **Harness 在外、Resilience 在内**：先做准入判定（顺序/循环），再进超时与熔断保护，
被硬拒的调用不白占一次熔断名额。Agent 级点位（`pre_think` / `post_reflect` / `on_finalize`）
落在 `orchestrator._consume_reply` 与 `final.result` 发布点。

### 2. 三类单步断言（能力清单第 2 项）

- Schema：按 `TOOL_REQUIRED_FIELDS` 校验关键字段，字段名逐个对过真实工具实现
  （`product_search` 回 `hits`/`recall_strategy`，`category_insight` 回 `insights`，订单三工具回 `Order.snapshot()`）
- Sequencing：`create_order_tool` 需先 `product_search_tool`；`cancel_order_tool` 需先 `query_order_tool`
- 断言失败**一律不 raise**，以 `[harness]` 前缀并入工具结果交模型自愈

**两处刻意偏离基线参考设计（修正示例缺陷）**：
1. 调用记录**按会话隔离**。基线参考设计用模块级 `_called_tools: list`，并发多会话会串台。
2. 写路径前置校验改为**「有证据才硬拒」**。基线参考设计说 `create_order` 必须硬拒，
   但会话可能从 `AgentState` 快照恢复（进程重启后内存记录为空），此时硬拒会误杀合法下单。
   规则收紧为：本会话已观测到工具调用却无检索 → 硬拒；完全无记录 → 降级为警告。

Semantic 断言：仅保留接口位置，未接轻量 LLM 判定（会引入额外模型调用），如需启用另行评估。

### 3. Silent-Drift（能力清单第 3 项，默认关）

四类信号：目标遗忘（关键词命中率 < 20%）、探索发散（连续 3 次空候选）、
偏好丢失（命中黑名单属性）、成本失控（近 3 轮均值 > 历史均值 × 2）。
前三类纯计算零成本；LLM 终审为**可选注入**，且仅在纯计算未命中时才调用（省钱）。
同样按会话隔离（基线参考设计的 `_round_counter` 是模块级全局）。

轮末命中只发事件 + 记日志，**不改写本轮回复**——本轮已结束，注入纠正提示来不及了；
漂移信号的价值在于被看见（进事件流与 trace，供 bad case 回收）。

### 4. LoopDetector（能力清单第 4 项）

滑动窗口（默认 6）内同一工具连续出现达阈值（默认 3）即注入收敛提示，**不强制终止**：
硬终止会杀掉「第 4 次调用本来就能成功」的正常重试。轮末重置（本轮内判定），按会话隔离。

### 5. Token 预算 + 四档降级（能力清单第 5 项，默认关）

档位与基线参考设计一致：`>50%` main / `20-50%` lite / `5-20%` minimal（注入简洁模式 hint）/ `<5%` fallback。
`ContextVar` 挂在当前意图上，子 Agent 派发时协程继承快照，共享同一账本。
作用点在 `llm.py::_invoke_upstream`：非 main 档切备用模型并发 `model.fallback` 事件（**降级不静默**）。

**已知限制（如实记录）**：`<5%` 档基线参考设计要求「不调 LLM，用已有中间结果做规则兜底」，
本轮只做到「切最便宜模型 + 注入简洁提示」，**未实现规则兜底应答器**——
那需要一套从中间结果组装回复的规则引擎，属独立工作量。

**实测踩坑**：真实网关返回的 `usage` 对象对缺失字段抛 **KeyError**，
而 `getattr(obj, name, default)` 只吃 AttributeError，导致记账异常冒泡、整轮对话变 `[error]`。
已加 `_safe_field` 宽容取值 + 全函数兜底，并补回归单测。

### 6. 请求排队优先级（能力清单第 6 项）

双 Redis Stream：`heng:intents`（正常）与 `heng:intents:large`（大请求）。
`xreadgroup` 里正常流排在前面——Redis 按传入顺序返回，天然形成优先级。
按对话轮数分流（`QUEUE_LARGE_REQUEST_TURNS`，默认 30），轮数计数存 Redis。
`_handle_one` / `_delivery_count` 均改为按消息所属流 ack，避免大请求流消息永不确认。

### 7. 熔断状态跨实例共享（能力清单第 7 项，默认关）

`SharedCircuitBreakerRegistry` 继承本地实现，把失败数与打开时刻放 Redis；
`ToolResilienceMiddleware` 通过 `_allow` / `_record_*` / `_status` 适配函数
优先 await `*_async`，无共享实现时回落同步方法，中间件本身无需感知。
**降级原则**：Redis 故障一律放行，绝不因熔断存储故障把正常调用全拒掉。

### 8. 安全护栏 L3 / L4（能力清单第 8 项）

- L3 `sanitize_tool_output`：7 条注入模式（中英），命中片段替换为 `[内容已过滤：疑似注入]`，
  **保留其余正常内容**，并提示模型忽略注入
- L4 `audit_output`：会话 ID / `sk-` key / 内部服务地址 / 内部工具名 → 脱敏，返回 `(是否安全, 文本)`

**刻意收窄范围**：基线参考设计示例含 `item_id`（本项目 schema 无此字段，不纳入）；
`product_id`（如 P1001）**不脱敏**——它本就随商品卡通过 `tool.result` 下发给前端渲染，属对外契约；
内部工具名按真实工具集逐个列出，不用 `\w+_tool` 宽泛模式，避免误伤买家可见措辞。

## 四、WON'T DO：四阶段对话状态机（能力基线项）

基线参考设计为 `INTENT → SEARCHING → ADVISING → TRADING` 四阶段，每阶段只开放工具子集，
并以「ADVISING 屏蔽写工具」作为防过早下单的硬保障。**经评估决定不实现，相关参考设计同步拆除**，理由：

1. **阶段判定依赖启发式**。「意图是否已澄清」「候选是否已就绪」没有可靠判据，
   误判即错误地屏蔽工具，可能把主流程卡死。
2. **与既有权限引擎职责重叠**。写操作的真实硬保障已经存在且更直接：
   `permissions.py` 的 `PermissionRule` / `_AUTO_ALLOWED_TOOLS` 白名单 + 确认卡语义 + 幂等键。
3. **收益不确定、风险明确**。相比之下，Sequencing 断言（写操作需先检索）以更小代价
   覆盖了同一类 bad case，且失败可降级为警告。

该基线项保留编号，条目改述为「动态工具权限与写操作硬保障」，讲代码里真实存在的机制。

## 五之三、长期记忆能力（本轮补齐 #13）

先描述升级前现状：长期记忆已有写入（`remember_preference_tool`）+ 读取注入（`orchestrator._build_inputs`），
但缺三块：无法撤回、无相关性筛选（全量注入）、子 Agent 拿不到偏好（靠主 Agent 抄进 demands 的软约束）。

### 关键取舍

- **dislike 不参与 top_k 截断**：黑名单与 query 相似度低，纯 top_k 会把它丢掉→推出用户明确拒绝的商品。漏黑名单是安全问题，不是相关性问题。
- **read_relevant 不上持久化端口**：挂在 `PreferenceStore` 会迫使 JSON/PG 实现依赖 embedding；改为应用层 `PreferenceSelector`（相关基线条目描述已同步更新）。
- **删除按 statement 不分 kind**：同一句话可同时存 like/dislike（存量单测已证实），撤回时一并清除。

### 附带修复的真实缺陷（跑四轮才暴露）

`semantic_cache.py` 的分桶 key 只带模型名与提示词指纹，**没带买家偏好状态**。后果：买家撤回
“不要塑料”后再问一句语义相近的话，命中撤回前的旧回复——里面还写着“符合您不要塑料的偏好”，
直接向用户断言了一条它刚删掉的偏好。修法：把全量偏好指纹加进分桶 scope（用全量而非选中子集，
子集随 query 变会把缓存打碎）。回归用例：`test_phase4_cache.py::TestPreferenceScopedCache`。

### 前提改动：商品库 10 → 60 SPU

`app/infrastructure/persistence/seed_products.py` 新增 50 个 SPU（`P1011`~`P1060`）。
原有 `P1001`~`P1010` 的 id 与字段**未动**（多条单测依赖其排序断言）。
原因：10 个 SPU 下 Recall@10 恒等于 1，指标无区分度，评测形同虚设。

### 真实跑测结果

商品检索（Docker Qdrant + 真实 `text-embedding-v4`，67 条，K=8；初建读数，现为 105 条标注，见上表）：

| 档位 | Recall@8 | MRR | NDCG@8 | lexical R | semantic R |
|---|---|---|---|---|---|
| embedding_rerank | 0.978 | 0.952 | 0.937 | 0.973 | 1.000 |
| embedding_only | 0.978 | 0.952 | 0.937 | 0.973 | 1.000 |
| keyword_2gram | 0.871 | 0.841 | 0.821 | 0.982 | **0.361** |

硬约束过滤准确率三档均 1.000。品类知识库（22 条，K=5）：Recall 0.977 / MRR 0.970 / NDCG 0.966。

核心结论：**降级到关键词在语义类 query 上丢约 64% 召回（1.000 → 0.361），
字面类几乎无损（关键词甚至微胜 0.982 vs 0.973）**。

### 已知局限（如实记录）

- `_RECALL_TOP_N = 8` 限制向量召回深度，故 K 取 8。K>8 时向量档不可能再涨，
  而关键词档是全库打分无上限——在 K=10 对比会系统性偏袒关键词档。
- `embedding_rerank` 与 `embedding_only` 数字相同，因未配置 `RERANKER_BASE_URL`（脚本已告警）。
- 知识库仅 5 篇文档（9 个 chunk），Recall@5 接近饱和（K=2 复测 0.932），
  当前语料规模下 **MRR 才是有信息量的指标**。
- 60 SPU 仍偏小；阈值 0.75/0.65/0.70 是防退化护栏，不是“达标即优秀”证书。
- 67 条标注为单人完成，**无标注一致性检验**；语义类仅 12 条，做模型选型决策前应扩到 50 条。
  （**二十期已落实**：扩到 105 条，语义类 50 条，七档重跑逐位一致。）

### 附带修复的真实缺陷

`app/infrastructure/embedding/openai_embedding_client.py`：embedding 网关在单批 >10 条时
返回 **HTTP 200 + `content-type: application/json` + 空 body**，`raise_for_status()` 放行，
最终在 `.json()` 抛 `JSONDecodeError`；而 `bootstrap_product_index` 会吞掉异常降级关键词召回，
表现为**向量检索静默失效**。原种子库恰好 10 个 SPU（正好卡在上限内），所以一直未暴露。
修法：按 `EMBEDDING_MAX_BATCH`（默认 10）分片串行 + 空 body 时报出可行动的错误信息。
