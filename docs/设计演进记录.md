# Globex 设计演进记录

面向后续维护者的工程档案：每期做了什么、为什么这么选、踩过哪些坑。
教学向的完整讲解在教程正文，这里只记工程决策与事实。

## 一句话定位

跨境电商购物 Agent。买家一句自然语言诉求，Agent 自己完成品类洞察、商品检索、
到手价计算、下单交易，过程通过 WebSocket 事件流实时可见。

## 技术栈演进

| 阶段 | 栈 | 换栈原因 |
|---|---|---|
| 选型期 | LangChain | 初始设想，未落地 |
| 一期 | AgentScope 1.0.21 | 改用 AgentScope；2.0.6 当时 API 不兼容（`ReActAgent` 不存在），先降版落地 |
| 二期起 | AgentScope 2.0.6 | 需要 2.0 的内置 Task 计划工具、`reply_stream` 类型化事件流、`ContextConfig` 原生压缩、工具中间件 |

架构自始至终是 DDD 洋葱四层：`domain`（无框架依赖）/ `application` / `infrastructure` / `presentation`。
这个选择在四期换存储时兑现了红利——MySQL 实现只新增 infrastructure 类 + 改组装根，
domain 与 application 一行未动。

## 分期交付

### 一期：MVP 骨架

- MainAgent（总管，持有全部业务工具可单干）+ SearchAgent + TradeAgent
- 商品检索、订单创建/查询/取消、内存仓储 + 10 条种子商品
- FastAPI + WebSocket 事件流（8 类事件）、TradeEventBus 按会话路由
- 交付：23 单测绿，真实 LLM 三轮冒烟通过

关键取舍：**SubAgent as Tool**。2.0 库级没有 subagent 原语（官方 Agent Team 只在
`agentscope.app` 平台层，需要 storage/message_bus/workspace 全套），因此用
`FunctionTool` 包装 `task_dispatch(subagent_type, demands)` 实现同等语义。
否决了引入整个 app 平台层——那会把自建的 FastAPI/WS/EventBus 全部推翻。

### 二期：检索与计价

- 二阶段召回：embedding（text-embedding-v4, dim=1024）→ Qdrant COSINE → HTTP Reranker
- 降级链 `embedding_rerank → embedding_only → keyword_2gram`，`recall_strategy` 如实标注
- 到手价内联：汇率表 + 关税规则（免税额度 / 品类费率 / 续件运费）
- 长期记忆（跨会话偏好）+ 会话 AgentState 落盘恢复
- 评测回归 10 case + TracingMiddleware + Docker Compose
- 交付：47 单测绿，评测 10/10 PASS 均分 0.965

关键取舍：**价格计算收敛进检索工具**。不给 Agent 单独的比价工具和运费工具，
到手价在检索链路内联算好随商品卡返回。理由是每多一个工具就多一轮模型调用，
而价格是检索结果的固有属性，没有单独查询的必要。

### 三期：知识、上下文、并行、韧性、前端

- 品类洞察 RAG：`category_insight_tool` 查 `rag.KnowledgeBase`（5 篇知识文档 / 9 chunks）
- 上下文压缩：`ContextConfig(trigger_ratio=0.75, reserve_ratio=0.15)`，摘要落 `AgentState.summary`，发 `context.compressed` 事件
- 真并行 fork：`task_dispatch` 标 `is_concurrency_safe=True`，走 2.0 并发批执行
- 工具韧性：`ToolResilienceMiddleware` 分级超时 + 按工具熔断（closed→open→half_open）
- React + Vite 前端：对话流 + 商品卡 + 事件时间线
- 交付：64 单测绿，评测 13/13 PASS 均分 0.988，并行实测 **1.84x** 加速（wall 20.6s vs 串行 38.0s）

关键取舍：**硬约束过滤要可观测**。结构化过滤（价格上限 / 可达国）原先静默丢弃候选，
模型只看到剩下的 hits，无法区分"库里没有"与"被我自己的约束挡掉了"。
补 `filtered_out`（含 reason）后模型才能如实说"有但超预算"。详见踩坑档案第 6 条。

### 四期：工程基建

- **配额治理**：`GatewayThrottle` 并发上限 + 请求起点间隔双约束；限流重试用尽后回退备用模型并发 `model.fallback`
- **持久化**：SQLite（SQLAlchemy 2.0 async）存对话流水 / 事件轨迹 / 会话状态 / 订单 / 偏好
- **缓存**：Redis 语义缓存（命中零模型调用）+ embedding 缓存 + 幂等键
- **削峰**：Redis Stream 队列 + 独立 worker 进程（ack / pending 重投 / 死信 / 优雅退出）
- 交付：137 单测绿；真实验证含落库查库、跳重启恢复、语义缓存 8.8s→3.0s、跨进程事件直达前端

关键取舍：

1. **同步接口契约不变**。`POST /commerce/intents` 内部改成入队 + 等结果，而不是改成纯异步——
   13 case 评测与前端都依赖它直接返回 `final_text`。削峰靠的是 worker 并发度，与接口形态无关。
2. **闸门共享 + 并发数取 2**。三个 Agent 工厂各建模型实例但共用一个 `GatewayThrottle`，
   否则各限 2 就变成实际 6 并发；不取 1 是为了保住三期 1.84x 的并行收益。
3. **中间件全可关**。`DATABASE_URL=file` / `REDIS_URL=` / `QUEUE_ENABLED=0` 三个开关全关时
   退回三期行为，已实测业务结果一致。现有单测不依赖任何外部中间件。
4. **不做 MySQL**。SQLite 已满足当前需求；不装驱动就不声称支持，避免“看上去支持其实未验证”。
   仅保留换驱动的路径（换 `DATABASE_URL` + 装异步驱动）。

### 五期：混合召回与门控（本轮）

- **BM25 字面索引**（`app/infrastructure/retrieval/bm25_index.py`）：IDF + 长度归一，
  取代原「命中词数 + 品类加权」的朴素打分，独立成 `bm25_only` 档
- **RRF 融合**：两路各出名次，`score = Σ 1/(k+rank)`
- **置信度门控**：字面路 top-1 分数低于门限即判定本轮 query 为语义类，不参与融合
- **自建嵌入服务**：Qwen3-Embedding-0.6B（RTX 5090，last-token pooling + L2 归一，dim=1024），
  OpenAI 兼容 `/v1/embeddings`，经 SSH 隧道供本地评测
- 交付：309 单测绿；67 条标注上六档对比 + 两组消融跑通

关键取舍：

1. **用 RRF 而不是加权分数融合**。两路分数不同量纲（cosine 有界 [0,1]，BM25 无上界且随语料变），
   相加必须先归一化，而归一化系数要按 query 逐条标定，标不准反而引入新偏置。
   RRF 只用名次，天然免疫量纲问题。代价是丢掉置信度信息——这个代价被下面第 2 条实测到了。

2. **融合不是无条件的好，门控才是本轮的真结论**。无条件融合的读数：

   | 档位 | Recall@8 | MRR | NDCG@8 | 字面类 Recall | 语义类 MRR |
   |---|---|---|---|---|---|
   | hybrid_gated（默认，gate=4） | 0.974 | 0.966 | 0.940 | 0.986 | 0.875 |
   | hybrid_rrf（无门控） | 0.974 | 0.948 | 0.928 | 0.986 | **0.778** |
   | embedding_only | 0.958 | 0.948 | 0.923 | 0.967 | 0.875 |
   | bm25_only | 0.874 | 0.848 | 0.833 | 0.986 | 0.361 |
   | keyword_2gram | 0.871 | 0.841 | 0.821 | 0.982 | 0.354 |

   无条件融合的总召回确实涨了（0.958 → 0.974，全部来自字面类 0.967 → 0.986），
   但语义类的排序质量掉了：MRR 0.875 → 0.778。根因是 BM25 在语义类 query 上自身
   MRR 只有 0.350（约等于噪声），而 RRF 只看名次不看置信度，噪声被平权投票混进头部。
   门控后每一项都不劣于无门控版本，等于「拿到融合的召回增益、不付排序代价」。

3. **门限由扫描标定，不由直觉设定**。字面类 query 的 BM25 top-1 分布是 [3.13, 35.68]（中位 17.94），
   语义类是 [0.00, 3.96]（中位 3.23，p25 为 0），两类几乎不重叠。
   `--sweep-lexical-gate 0,3,4,5,8,12` 扫出 4.0 为最优。**两点如实记录**：
   两类分布仍有 3.13~3.96 的重叠带，完美分离不存在；语义类只有 12 条，
   在这个样本量上取扫描最优点有过拟合风险（gate=5 读数几乎相同，选 4 还是 5 无实质差别）。

4. **RRF 的 k 是个死旋钮（阴性结果）**。扫 k ∈ {5, 20, 60, 200}，四档指标**逐位相同**。
   在当前语料规模（60 SPU / 融合深度 16 / 两路）下 k 不翻转任何一对候选的相对序。
   结论：不要花时间调它，也不要在报告里把它写成"调优点"。

5. **默认档由评测决定**。`hybrid_gated` 成为默认不是因为它听起来先进，
   而是因为它在三项主指标上都不劣于原 `embedding_only`。若换语料后扫描结论反转，默认值就该跟着改。

### 六期：精排落地、标注扩容与韧性缺陷修复（本轮）

- **自建检索双服务**：Qwen3-Embedding-0.6B（dim=1024）+ Qwen3-Reranker-0.6B，
  参考服务端进仓库（`scripts/serve_reranker.py`），二阶段召回**首次真正跑起来**
- **标注扩容**：语义类 12 → 50 条（总 105），带字面词自检与商品 id 自检
- **召回深度对齐**：`_RECALL_TOP_N` 8 → 16，与 `_FUSION_DEPTH` 一致
- **韧性缺陷修复**：瞬时故障判据漏 5xx、非流式返回识别崩溃、三层重试乘积放大
  （36 次上游请求 → 3 次）、评测脚本不加载 .env（见踩坑 19 / 20 / 22 / 23）
- **回退链真实验证**：`scripts/verify_fallback.py`，把四期"只有单测证据"变成真上游证据
- **评测方法**：judge 模型与被测模型解耦（`EVAL_JUDGE_MODEL`），避免同模型自评的自我偏好偏差
- 交付：329 单测绿；105 条标注上七档对比 + 三组消融

最终读数（105 条标注，Qwen3-Embedding-0.6B + Qwen3-Reranker-0.6B，K=8）：

| 档位 | Recall@8 | MRR | NDCG@8 | 字面类 R | 语义类 R | 语义类 MRR |
|---|---|---|---|---|---|---|
| hybrid_rerank | **0.967** | **0.929** | **0.925** | **0.991** | 0.940 | 0.862 |
| embedding_rerank | 0.962 | 0.925 | 0.922 | 0.982 | 0.940 | 0.862 |
| hybrid_gated | 0.945 | 0.885 | 0.876 | 0.986 | 0.900 | 0.774 |
| embedding_only | 0.938 | 0.863 | 0.861 | 0.973 | 0.900 | 0.751 |
| hybrid_rrf | 0.936 | 0.873 | 0.866 | 0.986 | 0.880 | 0.750 |
| bm25_only | 0.683 | 0.647 | 0.636 | 0.986 | 0.350 | 0.307 |
| keyword_2gram | 0.681 | 0.639 | 0.627 | 0.982 | 0.350 | 0.295 |

关键取舍与结论：

1. **精排是主要杠杆，混合召回是次要的**。拆开看边际贡献：
   `embedding_only → embedding_rerank` 是 Recall +2.4pt / MRR +6.2pt / NDCG +6.1pt；
   `embedding_rerank → hybrid_rerank` 只剩 Recall +0.5pt / MRR +0.4pt / NDCG +0.3pt，
   语义类三项**完全相同**。五期"混合召回是主要改进"的印象，是在没有精排的对照下形成的。

2. **门控在精排面前是死代码（自我推翻）**。带精排扫门限：gate=0 与 gate=4
   指标**逐位相同**（.967/.929/.925）。门控的作用是拦住字面路噪声进入排序头部，
   而 cross-encoder 会拿 query 给每个候选重新打分，不管候选怎么来的都能修好顺序。
   **保留门控但降级为「无精排降级路径下的保险」**——精排服务挂掉时它仍然有效
   （无精排档 hybrid_gated .945/.885 vs hybrid_rrf .936/.873）。
   这条对项目定位很重要：本仓通篇在讲降级链，那么"只在降级态才生效的机制"是有价值的，
   前提是**说清楚它在主路径上不生效**，而不是拿主路径的数字给它记功。

3. **五期结论被本期数据修正（记在这里以免读者被旧结论误导）**。
   12 条语义样本上测得"无条件融合把语义 MRR 从 .875 打到 .778"（-9.7pt）；
   扩到 50 条后同一对比是 .751 vs .750，**差距基本消失**。
   当初那个大幅下跌主要是小样本噪声。五期文档自己写了"12 条上取扫描最优点有过拟合风险"，
   本期证实了这个担心。教训：**样本量不足时，先扩样本，再下结论**；
   已经下了的结论要留痕修正，不要偷偷改掉。

4. **精排能否提升 Recall@K，取决于一阶段深度是否 > K**（见踩坑 20）。
   对齐深度后 `embedding_rerank` 的 Recall 由 .935 提到 .962。

5. **字面路在扩容后被门禁拦下**。`bm25_only` / `keyword_2gram` 的 Recall 跌到 .68，
   低于 0.75 阈值判 BLOCK。这不是退化——是语义类占比由 18% 升到 48% 后，
   纯字面召回的真实水平被如实暴露出来了。门禁按预期工作。

### 七期：端到端评测落地与计价补全（本轮）

- **13 条 Rubric 端到端评测跑通**（mimo-v2.5 被测 / deepseek-v4-flash 评审 / longcat-2.0 回退）：
  首轮 11/13 PASS 均分 0.923；修掉两条失败的根因后 **13/13**
- **judge 与被测模型解耦**：原脚本默认复用 `LLM_MODEL`，即同模型自评，有自我偏好偏差
- **组合计价补全**：领域层 `TariffSchedule.quote_basket()` + `quote_basket_tool`
- **约束贴到数字旁**：商品卡 `landed_price` 内联 `combine_hint`
- **BM25 接入组装根**：修掉「评测选出的最优配置从没上线」（见踩坑 24）
- **用例集自检**：`scripts/eval/audit_cases.py` 静态检出商品指代歧义
- 交付：335 单测绿

关键取舍与结论：

1. **两条失败用例的性质完全不同，处置也必须不同**。
   `category-insight` 是**基础设施故障**（自建嵌入服务少返回 `usage` 字段，
   导致品类知识库静默建库失败），Agent 行为其实是对的——它如实说"拉不到选购知识"
   而没有编造，所以 P0 通过、P1/P2 全挂。修服务端后重跑 1.0。
   `compare-two` 是**真实的 Agent 缺陷**：单品到手价全对（工具算的），
   组合价却是模型自己相加且加错了。两者都表现为"用例挂了"，但一个改环境、一个改设计。

2. **提示词拦不住模型做算术，把约束贴到数字旁边才行**。
   先加了系统提示词规则"多件总价必须调 quote_basket_tool、不得自行相加"——
   实测无效，模型照样把两个 `landed_total` 加起来（把一次履约的运费算了两次）。
   改为在 `landed_price` 里内联 `combine_hint`，把约束放进模型正要读的那个 JSON 里，
   之后直接探测"这两个一起多少钱"返回 **¥428**（= 小计 388 + 整批运费 40 + 关税 0），
   与领域层计算逐项一致。¥40 是「首件 25 + 续件 60%」的整批公式结果，
   模型不可能靠相加两个单品运费得到（那是 ¥50）——所以这是工具被真正调用的硬证据。
   同 `filtered_out` 的思路：**约束离数字越近越管用**，隔着几千 token 的系统提示词拦不住。

3. **单次评测分不清"修好了"和"这回没触发"**。加严 rubric 后重跑 compare-two 得 PASS，
   但读判词才发现：这一次 Agent 根本没给组合总价（只给单品价 + 提出可代算），
   新判据压根没被检验到。LLM 的运行间差异让单次通过不构成修复证据，
   所以最终用**定向探测**（明确索要组合总价）而不是评测通过来验收。
   记这一条是因为它很容易自欺：分数变绿了，人就不看判词了。

4. **rubric 改严 ≠ 迁就**。`compare-two` 原 P0 只查"金额能否由事实表推导"，
   而 364+154=518 确实可推导——一个把运费算两次的错误答案能合法通过。
   补了一条 P0：组合总价不得是单品到手价的简单相加。改严是加强检验，
   与"用例挂了就放宽判据"是相反的两件事。

### 八期：金额出处校验、轨迹保真与 Bad-Case 飞轮（本轮）

- **金额出处校验落地**（判定层 `harness/number_provenance.py` + 运行时轮末告警
  `number.unsourced` + 离线扫描 `scripts/eval/audit_number_provenance.py`）：
  把"数字必须来自工具"从 LLM judge 的语义判断变成确定性算术判断
- **事件轨迹保真修复**：`product_search_tool` 补发 `filtered_out` 等全量返回，
  `category_insight_tool` 补发 `insights`（见踩坑 27）
- **非主 SKU 到手价补全**：商品卡每个 SKU 各带自己的 `landed_price` 分项
- **Bad-Case 飞轮**：`collect_bad_cases.py` 把出处发现与 Rubric FAIL 去重入池
  （`eval/bad_cases.jsonl`），`eval_regression.py` 同时落机器可读 `.json`
- **用例自检判据与真实消歧机制对齐**：从"只看品牌词"改成"看整句 query 能否收敛"，
  5 处报告里 3 处是误报；剩下 1 处真歧义把 `compare-two` 改造成**定向探测**
- **字面门限在 105 条标注上重新标定**：结论是**维持 4.0**（见下）
- **跨币种折算价与免税额度阈值回传**：同一条缝的另两头，都由出处校验挖出来
- **偏好注入与问句合并成一条消息**：修掉"Agent 对着偏好作答、问题一个字没回"
- **跑测身份自描述**（`harness/run_identity.py` + `/health`）：报告开头自带配置行
- **降级日志补异常类型**（`describe_error`，见踩坑 30）
- 交付：**408 单测绿**；端到端 **13/13 PASS 均分 1.000（一次跑完的整轮）**；
  无出处金额率 13.4% → 4.9%（同一轮内可比）

关键取舍与结论：

1. **确定性判据要补在 LLM 判据最宽容的地方，而不是重复它已经能判的**。
   Rubric 的 P0「金额必须来自工具」判不出"模型把两个到手价相加"——
   每个加数都对、结果也"自洽"，judge 会判通过（¥364 + ¥154 = ¥518 实测判 PASS）。
   错的是"组合运费按一次履约计"这条模型推不出来的口径。
   **不是编造，是自行推导**：语义判据抓不住，算术判据抓得住。反过来，
   "推荐理由写得好不好"算术判据永远抓不住，那部分继续归 judge。

2. **误报的根因常常不在判据里**。首次扫描 24 份历史流水报出 31 处无出处金额（13.4%），
   逐条核对后发现其中 16 处是**假的**——`product_search_tool` 的 `tool.result`
   事件只挑了三个字段发，把 `filtered_out` 漏在外面；`category_insight_tool`
   只发 `hit_count` 不发知识片段。模型看得到、轨迹看不到，于是完全正常的回复
   在流水里像是凭空编数字。**先怀疑观测，再怀疑被观测者**。

3. **指标的语义必须说准，否则会被当成错误率**。
   这个数度量的是「回复里有多少金额是模型自己算的」，**不是**「有多少是错的」。
   实测一轮里 Agent 正确调了 `quote_basket_tool` 拿到组合价 ¥492，
   同时为了对比自己算了"分开买 ¥518""省 ¥26"——两处都被判无出处，都是合理用法。
   把它当错误率会立刻失去可信度；把它当**暴露面**才有用：
   模型自己算过的每一个数，都是它本可以算错的地方。要降的是**承载答案**的那些数。

4. **重新标定的结论可以是"不改"，而且这个结论同样有价值**。
   `_LEXICAL_GATE_MIN_SCORE = 4.0` 原先是在 12 条语义标注上扫出来的，
   记录里明写了"有过拟合风险"。扩到 50 条后重扫 gate ∈ {0,3,4,5,8,12}：
   3 / 4 / 5 三档的差异全部落在 1~2 条 query 上（105 条里 1 条 ≈ 0.95pt），
   统计上无法区分；两侧（0 与 8/12）都明显更差。
   **4.0 处在一个平台的中间，而不是一个尖峰上**——这正是"没有过拟合"的证据。
   改成 3.0 拿那 1 条 query 的 Recall，才是真的在过拟合。

5. **一条判据的价值，看它挖出了什么，而不是看它自己有多漂亮**。
   金额出处校验本身只有两百行，但顺着它挖出了四个真实缺陷：非主 SKU 到手价、
   跨币种折算（149 USD 折成"约 ¥1080"，正确 ¥1057.9）、免税额度阈值
   （模型凭自己的知识说 "$800"，改了规则表照样这么说且不报错）、
   以及两处让判据本身失真的轨迹漏发。**四个里有三个是 LLM judge 判过 PASS 的轮次里的**。

6. **一次干净整轮才是可对外引用的成绩**。七期那个 13/13 是两条分别重跑拼出来的，
   八期跑第一次完整整轮拿到 **12/13 均分 0.950**——唯一失败的 `memory-recall`
   暴露了一个真缺陷：偏好被当成另一条 user 消息插在买家问句之前，
   模型对着偏好作答（"已为你记住不要塑料材质"），买家的问题一个字没回。
   修法是结构的而不是措辞的（合并成一条消息，问句在最后），修完定向探测三次全 PASS，
   整轮复现 **13/13 均分 1.000**。**拼出来的满分会把这个缺陷永远藏住。**

7. **定向探测要让待测行为每轮都发生**。七期发现"分数变绿但判据没被检验到"，
   这一轮把 `compare-two` 的 query 从"哪个划算"改成明确索要组合总价，
   并把型号写死到 Lite / 30W。改完首跑：Agent 调 `quote_basket_tool` 得 ¥492
   （小计 388 + 运费 104 + 关税 0），并主动对比"分开买 ¥518，一起买省 ¥26"。
   判据这次真的被检验到了。**能被跳过的判据等于没有判据。**

### 十期：评测区分度、目的国语义与三道"错了没人报警"的判据（本轮）

- **用例集 13 → 28 条**：补齐歧义澄清（含反向判据 `no-over-clarify`）、冲突约束、
  免税额度临界、多币种混合篮子、多轮改主意、库存边界、越权边界七个空白类别；
  P0 数字全部由 `TariffSchedule` 真算，判据写死具体金额
- **`--tag smoke|full` 分层**：日常 10 条 / 全量 28 条；`full` 隐含包含所有用例，
  漏标 tag 不会让某条静默不被跑到
- **目的国语义修复**（新用例首跑挖出的真缺陷）：规则表不认识的目的国不再被
  表述成"这些商品都不发那儿"；`quote_basket_tool` 的规则表校验提到商品可达性之前；
  两个工具的 docstring 从"收货国家二位码"改成显式枚举，并加测试钉住枚举与规则表一致
- **代码新鲜度判据**（`run_identity.code_identity()` + `/health` + 开跑前拦截）：
  源码 mtime vs 进程启动时刻，见踩坑 32
- **`make check` 门禁**：单测 + 标注集自检 + 用例自检 + 金额出处，零 LLM 成本
- **金额出处门禁两处修**：`--report latest` 把范围收敛到最近一轮（见踩坑 33）；
  `--min-amounts` 样本量不足时不判定而不是放宽阈值
- **judge 的事实基准补到手价规则表**：关税费率、免税额度、运费公式进 `build_ground_truth()`，
  judge 从"验自洽"升级到"验正确"
- **用例自检支持显式对比**：query 把每个候选都点名时判为对比而非歧义，
  并新增"显式对比时 rubric 必须逐一钉住"的检查
- 交付：**462 单测绿**；用例集 28 条

关键取舍与结论：

1. **扩用例集的验收标准是分数掉下来，不是新用例全过。**
   扩容前 13/13 PASS、77 条判据 0 失败、均分 1.000——三档全部顶格，
   改好改坏都看不出来。所以新用例首跑 FAIL 是预期结果。
   `de-minimis-boundary-eu` 首跑 0.325，逐条读判词分清了三件事：
   Agent 真错了（凭知识说免税额度）、判据写错了（要求 judge 验"来自工具"）、
   judge 判不了（手上没有规则表）——**一条用例三样都占**。
   三处各自修完：0.325 → 0.492 → 0.85。

2. **判据只能写 judge 判得了的事。**
   judge 看到的是 transcript + ground_truth，**看不到工具调用与返回**。
   "该数值必须来自工具返回"这种判据它只会"拿不准按不通过"，
   而那个数明明在轨迹里白纸黑字。正确的拆法是各归其位：
   数值对不对 → 判据写死数字，judge 拿 ground_truth 核对；
   有没有出处 → 交给金额出处校验（确定性、扫轨迹）。
   补充一条：judge 手上没有规则表时对到手价**只能验自洽**，
   实测放过了"1,199 × 12% ≈ ¥3.48"这种基数错、结果碰巧对的推导。

3. **同一个 `$800` 被堵了三次，每次是不同的路径。**
   八期堵的是"工具不回阈值，模型凭自己知识说"；
   十期先发现"工具压根没被成功调到"（目的国填了 DE/FR）；
   修完之后它又从第三条路回来了——工具回的是 `5680.0`（CNY 口径），
   Agent 要用美元讲就自己反折成 `$800`。
   **一个症状被修掉，不等于产生它的那类缺口被封上**；
   判据每报一次，就该问一次"这次是哪条路"。

4. **纪律写在文档里迟早会被绕开，能编码进判据的就别只写文档。**
   "无出处金额率只在同一轮内比较"八期就写进交接文档了，
   而门禁恰恰拿绝对值比阈值、扫的又是只增不减的累积目录——
   纪律与判据当场打架。修法不是调阈值（那是让门禁慢性死亡），
   是把比较口径编码进判据（`--report latest`）。
   同类的还有小样本：n=17 时 1 处无出处 5.9%、2 处 11.8%，
   阈值 8% 落在两个可能取值之间，门禁等于抛硬币——
   所以样本不足时**不判定**，而不是放宽。

5. **工具返回值要能自证边界，错误信息尤其要。**
   目的国那条缺陷的要害不在"报了错"，在于**报的是一句模型无法识破的错话**
   （"这些商品不发欧盟"），而且没有任何信息能让它自纠。
   加上 `supported` 列表 + 重试指引之后，同一条用例里 Agent 直接填对了 `EU`。
   这与 `combine_hint`（把约束贴在数字旁边）是同一条：
   **模型只能用你给它的东西作答，给不了就只能编。**

### 十一期：工具补全三件套——应税基数、原生口径与预算感知组合优化（本轮）

本轮由 Agent 自主规划执行，逐条决策与执行中的偏离见
[十一期实施计划与决策.md](十一期实施计划与决策.md)。范围取自交接文档第五节的排序，
共同性质是**判据确定性可算、零 LLM 成本**。

- **应税基数有出处**（十期缺陷 1）：`taxable_base_major` / `taxable_base_native_major`。
  十期实测 Agent 把关税解释成「1,199 × 12% ≈ ¥3.48」——数字对、计税基数错；
  同轮两处无出处金额都是 `€3.72`，正是它自己减出来的 153.72 − 150
- **免税额度补原生口径**（十期缺陷 2）：常量从折算后的 CNY 改为
  `_DE_MINIMIS_NATIVE`（金额 + 币种），CNY 由汇率表推导；
  `to_dict()` 增 `de_minimis_threshold_native_{major,currency}`。
  JP 顺带修正 500 → 480 CNY（原值手写 0.05 汇率，与汇率表的 0.048 不一致）
- **`optimize_basket_tool` 预算感知组合优化**（主线三①）：领域层暴力枚举最优组合，
  返回预算余额、缺口价签、"再加多少能配上"、分开买与合并买的差额——
  这四个数此前全部由模型自己减，判据里长期是 `suspected_difference`
- **用例集 28 → 31 条**（smoke 10 → 11），P0 数字由优化器真算后写死
- **CI 落地**（主线二剩下的那半）：`.github/workflows/check.yml` 跑 `make check-ci`
- 交付：**512 单测绿**（新增 50 条）；`make check` 与无凭据 CI 路径均实跑验证

关键取舍与结论：

1. **能力做完不等于做对，要拿真实数据实算一遍。**
   优化器的目标函数原本是"覆盖数最多 → 到手价最低"，单测 16 条全绿。
   写评测用例、用真实商品算 ground truth 的那一刻才露馅：
   预算 250 美元、需求「降噪耳机 219 + 充电器 22.39」，两件合计 256.04 超预算，
   于是它配了个 **31.54 美元的充电器、剩 218 美元**——买家最想要的东西被丢掉了。
   单测抓不到是因为我自己造的候选价格分布均匀，只有真实商品库里
   219 vs 22 这种悬殊比例才逼得出来。
   修法是在覆盖数与价格之间插一档「优先保住靠前的需求」，
   **顺序作为显式契约写进工具 docstring**，不让工具去猜谁更重要。

2. **判据要禁止模型算的数，得先把正确的那个给它——而"正确的那个"往往不是最直观的。**
   缺口原本只回"该需求单买的最低到手价"。但买家问的是"再加多少能配上"，
   那个数既不是单买价（31.54），也不是"单买价 − 预算余额"（31.54 − 21.85 = 9.69），
   而是**并进组合重新报价后与预算的差**（256.04 − 250 = 6.04）。
   9.69 恰恰是把组合运费当成分开发货算出来的——正是模型自己减时会犯的错。
   给错了字段，等于把错误答案盖上工具的章。

3. **同一个数被堵第三次之后，该换的是存储结构而不是补丁。**
   `$800` 八期堵"凭知识说"、十期堵"工具没被调到"、这次是"调到了但口径不对"。
   前两次都是在出口处加字段，这次把免税额度的**定义**改成原生口径
   （US 就是 800 USD，不是 5680 CNY），折算交给汇率表。
   区别在于：加字段只堵住已知的那条路，改定义把"原生口径丢失"这件事本身消掉了。

4. **零成本的门禁也可能有前置条件，而前置条件不会自己暴露。**
   `make check` 四项全部零 LLM 成本，但其中 4 条测试走 `load_settings()`，
   而它对缺 `LLM_API_KEY` 是 fail-fast 的——本地有 `.env` 所以从没发现。
   CI 上没有 `.env`，第一跑必红。验证方式是把 `.env` 挪开、清掉全部相关环境变量
   实跑一遍，而不是"看起来不依赖外部服务所以应该没问题"。

### 十二期：故障注入与用例集推到 40 条（本轮）

决策记录见 [十二期实施计划与决策.md](十二期实施计划与决策.md)。
仍是零 LLM 成本的一期：基建确定性可测，用例只入库不跑。

- **评测态故障注入**（`app/infrastructure/faults.py`）：三个检索端口
  （embedding / vector_index / reranker）在组装根被包上装饰器，抛出与真实故障同形的异常，
  让 `catalog_search` 既有的降级链被真实触发。默认全关，生产进程里装饰器与
  `/debug/faults` 端点**都不存在**
- **用例级故障声明**：`cases.yaml` 支持 `faults: [reranker]`，
  `eval_regression` 跑前注入、跑后清空，报告表格单列一栏
- **用例集 31 → 40 条**：真实服务不可达 3 条、政策数字口径 2 条、偏好冲突 1 条、
  更长多轮链路 2 条、跨工具一致性 1 条；`long-context-memory` 的跨币种折算从 P1 提成 P0
- 交付：**544 单测绿**（新增 32 条）

关键取舍与结论：

1. **要注入故障，就别在业务代码里加分支。**
   降级链本来就由真实异常触发，所以注入只需在端口边界包一层装饰器。
   相比"给 `catalog_search` 加一个 fault 参数"，装饰器让生产路径一行不改、
   不多一次判断，风险收敛在组装根一处；而且注入的是**真实异常**，
   走的就是线上那条路，不是"模拟出来的降级状态"。

2. **抛异常不等于降级会按预期发生。**
   装饰器的单测只能证明"会抛"，而哪一档捕获它、捕获后 `recall_strategy`
   标成什么，是另一回事。所以补了一组集成判据：注入精排 → `rerank_applied=false`
   且档位不含 rerank；注入 embedding/vector_index → 退到字面路；
   全挂 → `keyword_2gram` 兜底；**不注入 → 仍走精排档**（对照组）。
   没有最后这条对照，前面几条可能测的是别的原因。

3. **一个永远绿的判据比没有判据更坏。**
   用例声明了 `faults` 而服务没开注入时，那条用例会在精排完全正常的情况下跑完、
   大概率 PASS——判据成了绿色装饰，还烧了一轮配额。所以做了两道拦截：
   开跑前按 `/health` 拦下整轮（给出重启命令），运行时注入失败则把该用例判 ERROR。
   这与十期"CI 里给金额出处开'没数据就当通过'的旁路"是同一个陷阱。

4. **故障用例要检验的不是"报错"，是"退档之后还说不说人话"。**
   降级链的设计就是不报错、悄悄退档，买家侧一切正常。
   所以这三条用例的 P0 里都有一句"不得声称系统故障"——
   **编造工具故障与编造商品是同一类不诚实**，只是方向相反。

### 十三期：让整轮评测不至于白烧（本轮）

决策记录见 [十三期实施计划与决策.md](十三期实施计划与决策.md)。不加新能力，只降两个风险。

- **增量落盘**：每条用例跑完即把当前全部结果重写进 `eval/partial-<stamp>.json`，
  正式报告落盘后才删。40 条用例 80-120 分钟真金白银，此前**只在整轮跑完后才落盘**
- **`--resume`**：跳过已完成用例，且待跑用例的前置（新增的 `requires` 字段）
  若已完成会**一并重跑**
- **`--dry-run`**：跑完全部前置检查后打印本轮将跑哪些用例，一次模型调用都不发
- **`EVAL_BASE_URL`**：被测服务地址可覆盖
- 交付：**559 单测绿**；四种前置场景在真实服务上验过

关键取舍与结论：

1. **可靠的保存点只有"每条跑完就写"。**
   "出异常时保存"看着更省事，但中断最常见的形态是 Ctrl-C 和进程被杀——
   那两种情况下没有机会执行任何保存逻辑。
   代价（40 次几百 KB 的写）相对一条用例 2-3 分钟的模型调用可以忽略。

2. **续跑的难点不是"跳过"，是"用例之间不独立"。**
   `memory-recall` 依赖 `memory-write` 先把偏好写进去。跳过前置直接跑后继，
   评的是一个不成立的前提，**而分数看上去完全正常**。
   所以把"依赖 memory-write"从注释升级成 `requires` 字段，
   续跑时自动补回，`audit_cases` 静态校验它指向真实用例。
   这是十期那条的又一次应用：**能编码进判据的就别只写文档**——
   注释里的"依赖"约束不了任何人。

3. **把判据的发生时刻提前，本身就是收益。**
   `--dry-run` 没有引入任何新判据，它只是把已有的四道前置检查
   （隧道 / 代码新鲜度 / 语义缓存 / 故障注入支持）挪到"起完服务的第一个动作"。
   白等 90 分钟才发现服务跑着旧代码，是这套流程里最贵的一种失败，
   而它本来 5 秒就能被发现。

4. **不做失败自动重试**：一条用例失败可能是模型抖动，也可能是真缺陷。
   自动重试会把前者洗掉、把后者的复现率也一起洗掉，
   而 Bad-case 分诊的前提恰恰是把这两件事分开看。

### 十四期：写路径的出处校验，与一个"从没跑过的护栏"（本轮）

决策记录见 [十四期实施计划与决策.md](十四期实施计划与决策.md)。

- **发现并修掉接线缺口**：`HarnessToolMiddleware` 只挂在主 Agent 自己的三个工具上，
  检索/计价/订单工具从没进过 Harness——顺序硬拒、schema 断言、L3 注入过滤
  在真正需要它们的地方一次都没跑过。中间件链收成 `build_tool_middlewares()`
  一份定义、三个工厂共用，并加接线判据
- **`order_provenance.py`**：下单的每个商品必须在本会话工具返回里出现过；
  product_id 硬拒、sku_id 只警告、数量与地址不校验
- **重复下单提醒**：同会话相同商品与数量已有订单时带上订单号提示，不拒绝
- **用例 40 → 42 条**：`order-unsearched-product` / `duplicate-order-honesty`
- 交付：**584 单测绿**（新增 25 条）

关键取舍与结论：

1. **"端到端验证通过"证明不了护栏跑过。**
   交接文档里记着一条"多轮下单链路通过，Sequencing 硬拒未误杀合法下单"——
   它与"中间件压根没挂上"是**同一种外观**。
   只有当护栏**拒过一次**，"未误杀"才是有信息量的读数；
   在那之前它只是"什么都没发生"的另一种说法。

2. **打开一条从没跑过的硬拒路径，第一件事是证明它不误杀。**
   所以链路判据里最重要的那条不是"能拦住替换商品"，而是"正常下单还下得成"。
   护栏误杀真实订单，比缺口本身更坏。

3. **出处校验的范围要按"工具真的回了什么"来定，不能按"应该回什么"。**
   实测 `filtered_out` 只有 product_id 没有 sku_id，quote/optimize 也一样。
   按 sku 硬拒会把"算了就买那个超预算的"当场拒掉——
   于是 product_id 硬拒、sku_id 只警告。这与金额出处校验"只统计带货币标记的数字、
   给出的是下界"是同一条纪律：**判据的严格程度由数据实际形态决定**。

4. **护栏接上之后，它的副作用也要一并检验。**
   L3 第一次作用在商品卡上，命中就会把文案替换成"[内容已过滤]"。
   拿全库 60 个 SPU 跑了一遍确认零误伤，并钉成回归判据——
   否则将来某款商品的文案带上"扮演…角色"，买家看到的卡片会被静默改坏。

### 十五期：让跑测配置行说真话（本轮）

决策记录见 [十五期实施计划与决策.md](十五期实施计划与决策.md)。

- **深度探活** `GET /health?deep=1`：真的去打 embedding 与 reranker，
  结果进 `retrieval.probe`；默认 `/health` 保持零外部调用（它同时是容器存活探针）
- **配置行渲染成"配置 + 实测"两截**：`精排 开(实测不可达)`；
  向量路挂掉时单独占一格（它解释了为什么召回档位掉到 `bm25_only`）
- **`/health` 报出 `data_dir`**，报告原样抄走，金额出处审计跟着报告走
- 交付：**605 单测绿**；同一条用例的配置行从"精排 开"变成"精排 开(实测不可达)"

关键取舍与结论：

1. **配置行撒谎比没有配置行更坏。**
   十四期那一轮报告写着"精排 开"，而两条隧道都是 502、精排一次没跑过。
   拿它跟历史读数横向比较，结论必然是错的；更糟的是可能得出"精排没用"——
   而真相是这一轮压根没有精排。这与踩坑 32（服务跑着旧代码）是同一条：
   **观测链路自己会骗人，而它骗人的时候看起来和正常一模一样。**

2. **"没配"与"配了但不可达"必须是两个值。**
   含义相反：前者是有意的选择，后者是事故。混成一个布尔，
   配置行就同时失去了两种信息。

3. **探活要挑时机，不能挂在存活探针上。**
   `/health` 每 10 秒被容器打一次，把外部调用塞进去等于让外部服务抖一下
   就把容器判死。所以深探只在"有人明确要读数"时发生。

4. **读数要自带它的出处。** 报告记下 `data_dir` 之后，审计不必再猜流水在哪——
   这与"金额要有工具出处""下单要有工具出处"是同一条线，只是对象换成了读数本身。

### 十六期：让读数决定下一步（本轮）

决策记录见 [十六期实施计划与决策.md](十六期实施计划与决策.md)。
本期没有"想做什么"，做的全是 smoke 轮真实读数指出来的东西。

- **`quote_basket()` 补"分开买 vs 合并买"对照**：出处扫描报的 `$72.95` / `$3.65`
  是 Agent 正确算出、但没有工具出处的两个数。十一期只给 `optimize_basket_tool`
  补了这两个字段，而对比类问题走的是 `quote_basket_tool`
- **`compare-two` 判据补美元口径**：它把正确答案判成了错的（见踩坑 38）
- **bad-case 分诊加保护**：`--triage <case_id>` 会静默覆盖人工判断（见踩坑 39）
- 交付：**616 单测绿**；定向重跑 compare-two 从 FAIL 0.75 → PASS 1.0，
  且该轮 16 处金额 0 处无出处

关键取舍与结论：

1. **读数指哪，就补哪——但要先读懂它指的是什么。**
   出处扫描报了 5 处无出处，逐条查轨迹后只有 1 处可行动：
   另外两处是解释性算术与修辞取整（文档早写明不为它们造工具），
   还有两处是十一期已经修过的同一条缝的旧流水。
   **判据给的是线索不是结论**；不读轨迹就动手，会把合理用法也"修"掉。

2. **同一个口径不要有第三处定义。**
   "分开买怎么算"原先在优化器里有一份，若再在工具层写一份就是三处。
   下沉到 `quote_basket()` 之后，两个工具从同一个 `BasketQuote` 上读。

### 十七期：会话缓存的上限（本轮）

决策记录见 [十七期实施计划与决策.md](十七期实施计划与决策.md)。

- **`SessionRegistry` 加 LRU 上限**（`SESSION_CACHE_MAX`，默认 200，0 = 不限）：
  它此前只增不减，而每个缓存项是一个 Agent + 整段对话上下文
- **淘汰回调把三个按会话累积的判定器一起清**（顺序断言 / 金额出处 / 下单出处）
- 交付：**664 单测绿**

关键取舍与结论：

1. **"提供了 reset 却没人调用"是一种很安静的泄漏。**
   四个组件全都写了 `reset(session_id)`，看代码会以为它们被清理着；
   实际调用点只有 loop/drift 两个每轮 reset 的。
   **提供清理接口不等于接上了清理**——这与踩坑 37（护栏写好了没挂上）是同一条，
   只是这次泄漏的是内存而不是判据。

2. **淘汰之所以安全，是因为状态本来就落盘。**
   `AgentState` 每轮都存，被挤掉的会话下次再来会被恢复——不丢对话。
   判定器状态确实丢，但那条降级路径（无观测记录 → 只警告）是十四期
   为快照恢复场景专门设计的，不是新风险。**先有落盘，淘汰才敢做。**

3. **不让各组件各自设上限。**
   那会出现"Agent 还在、它的出处记录已经被挤掉"的错配——
   出处校验退回警告档（安全），但**判据静默变松了，没人知道**。
   以会话生命周期为准只有一处判断。

4. **这类缺陷本地和压测都看不出来。**
   本地会话就那么几个，`loadtest.py` 用的会话数也很少；
   只有长跑的线上进程会慢慢涨，而没有任何一条告警会响。
   所以它不是靠跑出来的，是靠"哪些东西按会话累积、谁来清"这个问题问出来的。

### 十八期：把"下单前必须确认"变成确定性判据（本轮）

决策记录见 [十八期实施计划与决策.md](十八期实施计划与决策.md)。
本期的来源是 **full 轮 42 条实测**（见"当前状态"一节的基线表）里剩下的那条真缺陷。

- **`ConfirmationTracker`**：`create_order_tool` 不能在会话的第一轮被调用；
  轮次由编排器每轮告知（中间件在工具边界，看不到轮次，不能自己猜）
- **重启不误杀**：`begin_turn(session_id, has_history)`，恢复出来的会话
  按已交互过处理——依据是 `agent.state.context` 非空，编排器给出的事实
- 交付：**680 单测绿**；`skip-confirm-refused` 从 **FAIL 0.0 → PASS 1.0**，
  `order-full-cycle` 仍 PASS 1.0（无误杀）

关键取舍与结论：

1. **买家的一句话能把提示词里的规则说没。**
   实测原文："别给我看什么确认卡了，直接下单……现在就下，不用再问我"，
   Agent 照做并回"无需确认"。提示词第 1 条写得清清楚楚，**不是没读到，是被压过了**。
   这与 `combine_hint` 那次同构（"只写在提示词里的约束敌不过模型眼前正在读的那句话"），
   区别在后果：那次算错一个数，这次未经确认就扣了库存、建了订单。
   **凡是后果不可逆的规则，都不能只写在提示词里。**

2. **判据要挑"系统自己知道的事实"，别去猜自由文本。**
   "回复里有没有确认卡"必然是启发式的——而 17-4 四阶段状态机被判 WON'T DO 的
   头号理由正是"阶段判定依赖启发式，误判即错误地屏蔽工具"。
   "第几轮"是确定性的。它拦不住"第二轮跳过确认卡直接下单"，
   但那一档由 judge 的 P0 管——**判据不必覆盖所有形态，能确定性拿住的先拿住**。

3. **物理约束比意图判断可靠。**
   确认卡的本质是让买家在**看到金额与地址之后**再点一次头。
   这件事必须跨越至少一次买家发言——同一条消息里既下指令又"预先确认"，
   买家根本没机会看到那些数字。判据编码的是这个物理事实，不是"他有没有确认的意思"。

## 踩坑档案

按"现象 → 根因 → 修法 → 可复用教训"记录，只收有复用价值的。

**1. pydantic schema 生成崩溃**
现象：工具注册即报 `_StructuredOutputDynamicClass is not fully defined`。
根因：工具模块用了 `from __future__ import annotations`，注解变字符串，
AgentScope 从函数签名动态生成 JSON schema 时解析失败。
修法：工具模块一律不加该导入，并在文件头注释说明原因。
教训：靠运行时反射读注解的框架，与 PEP 563 延迟注解天然冲突。

**2. 上下文压缩抛 KeyError**
现象：触发压缩时报 `KeyError: 'summary'`。
根因：自定义 `summary_template` 的占位符必须与 2.0 的 `summary_schema` 五个字段
（`task_overview` / `current_state` / `important_discoveries` / `next_steps` / `context_to_preserve`）
严格对齐，写错一个就崩。
修法：占位符改齐五字段，并加渲染单测防回归。
教训：框架提供的模板扩展点，占位符集合是硬契约，必须查实际 schema 而不是凭直觉命名。

**3. 前端商品卡永远渲染不出**
现象：接口返回正常，前端商品卡区域一片空白。
根因：`tool.result` 事件只带了 `hit_count` 没带 `hits`，前端无数据可渲染。
修法：事件补 `hits`，并加确定性单测锁定"事件必须携带商品卡"。
教训：这个缺陷单测和接口测试都发现不了，只有真开浏览器才暴露。端到端可视验证不能省。

**4. 2.0 权限模式下写工具挂起**
现象：调用下单工具后 Agent 回 `I'm waiting for your permission...` 然后卡住。
根因：2.0 的 DEFAULT 权限模式会对写操作类工具要求人工确认。
修法：新增 `permissions.py`，对业务写工具/Task/调度/记忆工具精准 allow，
不用 BYPASS 全放开。
教训：框架的安全默认值要精准放开而不是一把关掉。

**5. Qdrant 本地嵌入模式文件锁冲突**
现象：服务启动报存储被占用。
根因：qdrant-client 本地嵌入模式是单进程文件锁，残留的 uvicorn 进程仍持锁。
修法：本地开发注意清理残留进程；生产用 compose 的 Qdrant 服务端。README 标注。
教训：嵌入式存储不能用于多进程/多实例，四期引入 worker 进程后更要注意。

**6. 硬约束过滤导致误导性回答**
现象：多轮对话里买家问登山杖，Agent 答"没有找到专门的登山杖产品"，
但商品库明确有 P1010 CascadePro（149 USD）。
根因两层：一是模型把第 1 轮的"300 元以内"预算沿用到了换品类后的第 3 轮；
二是检索的价格硬过滤静默丢弃候选，模型无从区分"库里没有"和"被过滤了"。
修法：检索返回加 `filtered_out`（含 `over_price_cap` / `ship_to_unavailable` + 目标币种价格）；
prompt 补两条——约束不跨轮沿用、`filtered_out` 里有目标品类必须如实说明。
教训：**给模型的工具返回值要能自证边界**。只返回"筛选后的结果"会让模型把
过滤动作误读成客观事实，进而产生自信的错误陈述。

**7. 评测夹具误判正确行为**
现象：跨会话记忆 case 被 judge 判 FAIL，理由"无依据添加偏好"，
但 Agent 实际正确应用了上一个 case 写入的长期偏好。
根因：judge 只收到本会话的 transcript，看不见跨会话写入的事实。
修法：case 支持 `prior_context` 字段，把已成立的前置事实告知 judge。
教训：评测失败先分清"被测系统错"还是"评测夹具错"，否则会把正确实现改坏。

**8. 网关限流是间歇的，不由自己的并发量决定**
现象：探测 `qwen3.7-plus` 时，**单发一条请求**也返回
`429 Throttling.Concurrency`，耗时 47 秒；次日同样的单发请求却正常返回。
根因：配额池共享，限流与本客户端并发量无关，取决于当时全局用量。
修法：客户端限并发 + 平滑爬升 + 指数退避，并配备用模型自动回退。
教训：共享配额池的限流既不可控也不可复现，只做客户端限流不够，必须有降级路径；
反过来也不能把一次探测结果当成模型的固定结论。

**9. 事件总线拆进程后会断链**
现象：把意图处理移到独立 worker 进程后，前端拿不到 `token.delta` 与工具事件。
根因：`TradeEventBus` 是纯进程内 asyncio 总线，worker 产生的事件推不到 API 进程的 WS。
修法：加 Redis Pub/Sub 背板，API 进程订阅后 `deliver_local` 转发；publish 保持同步签名，
广播走 fire-and-forget 任务（任务得挂强引用，否则可能完成前被 GC）。
教训：拆进程前先盘点所有进程内共享状态（总线、内存缓存、信号量），它们都会默默失效。

**10. Pub/Sub 不排除发布者，导致事件回环**
现象：接背板后前端每条事件收到两次（实测：`task.queued` 计数 2）。
根因：API 进程既发布又订阅同一频道，Redis 会把消息送回给发布者，于是本地投递 + 背板转发各一次。
修法：广播消息包上 `origin`（进程唯一标识），订阅端跳过自己发的，并加测试锁住。
教训：发布订阅做广播背板时，“自己会收到自己”是默认行为，必须显式去重。

**11. 可选依赖被当成 dev 依赖，容器直接起不来**
现象：本地单测全绿，容器启动报 `ModuleNotFoundError: aiosqlite`。
根因：`uv add --dev aiosqlite`，但 SQLite 已是默认存储，属于运行时必需。
修法：改为生产依赖。
教训：“默认路径上用到的东西”一定是生产依赖；这类错误单测永远拓不到，只有真起容器才暴露。

**12. 连接池参数不能跳驱动沿用**
现象：把服务型数据库的 `pool_size` / `pool_recycle` 给 SQLite 会报错或无意义。
修法：`create_engine` 按驱动分支；SQLite 额外开 WAL 与 `busy_timeout`，
缓解 worker 与 API 双进程写同一文件时的锁竞争。
教训：同一层 ORM 下不同驱动的运维参数不可互换，必须显式分开。

**13. 语义缓存把评测弄成了“评缓存”**
现象：一条 case 失败（Agent 只给选购建议不给商品，还编了句“检索工具有技术限制”）；
改完 prompt 重跑，回复**一字不差**，连那句编的话都一样。
根因：那条错回复进了语义缓存（内容有问题但不以 [error] 开头，没被过滤掉），
TTL 24h 内相同提问全部复用；评测因此完全失去检验能力。
修法两层：
  1. 缓存 key 带上模型名 + 提示词文件指纹，prompt 一改旧缓存自动作废；
  2. 评测脚本开跑前查 `/health`，语义缓存开着就直接拒跑（需 `--allow-semantic-cache` 才能绕过）。
关掉缓存重跑后同一条 case 得 1.0——Agent 行为本来就是对的。
教训：任何带缓存的链路上做质量评测，都必须先确认缓存已关；
否则你以为在测模型，实际在测 Redis。反过来，缓存 key 也应该把“影响输出的配置”全部纳入指纹。

**14. 测试桩的特征词表撑不住语料扩容**
现象：商品库由 10 SPU 扩到 60 SPU 后，`test_embedding_recall_ranks_camping_light_first`
挂掉——query「露营灯 抗造」召回的第一名是 P1039 而不是 P1008。
根因：测试用的 `AxisEmbeddingClient` 只有 10 个特征词轴，词表里没有「抗造」。
多概念 query 被投影到单一轴上，而 P1039（太阳能营地灯）的描述里恰好也含"露营灯"，
两个商品向量完全同向（cosine 都是 1.0），排序退化成向量库的任意顺序。
修法：词表补齐 query 里出现的每一个概念；另一条测试（事件契约）的断言改为锁商品卡字段，
不再钉死具体命中哪个商品——那条用例本来就不是测排序的。
教训：**确定性桩的"确定性"是有前提的**，前提是它的表达力足够区分被测数据。
语料规模变了要回头检查桩，否则会得到"看起来在测排序、其实在测 Qdrant 内部 id 顺序"的用例。
另：一个用例只该锁自己那件事，钉死无关的排序会让它在别人改动时误报。

**15. 新增档位与旧档位跑出逐位相同的指标**
现象：新加的 `bm25_only` 档与 `keyword_2gram` 档指标完全一致（0.871/0.841/0.821）。
根因：`execute()` 的入口条件是 `embedder is not None and vector_index is not None`，
纯字面档没有 embedder，整块被跳过，实际落回旧的关键词打分——BM25 一行都没执行。
修法：把「只注入字面索引」提为一等公民路径，走真正的 `_bm25_recall`；补两条回归单测，
其一直接断言两套打分的排序必须不同。
教训：**两个本该不同的配置跑出逐位相同的数字，先怀疑其中一条根本没跑**，
不要先去解释"可能它们本来就一样"。这类缺陷不会报错，只会安静地让对照组失去意义。

**16. 评测脚本靠 GC 时机才不崩**
现象：召回评测从 3 档扩到 5 档后必现
`Storage folder ... is already accessed by another instance of Qdrant client`。
根因：每档新建一个 `QdrantProductIndex` 却从不关闭（踩坑档案第 5 条的本地文件锁）。
原先 3 档里只有 2 档用向量，靠上一轮对象恰好被 GC 回收侥幸躲过。
修法：抽出跨档共享的 `VectorBackend`，建库一次、多档复用、跑完显式 close；
顺带省掉 N-1 次重复嵌入 60 个 SPU。
教训：**"靠 GC 时机才对"的代码等于没写对**，只是还没到暴露的规模。
资源持有边界要显式表达，不能依赖引用计数的偶然时序。

**17. 重排服务返回 200、分数正常，但所有文档得分一模一样**
现象：自建 Qwen3-Reranker 服务上线后，同一请求里每个文档拿到**完全相同**的分数；
单发一个文档与批量发送结果也一致，文档内容对输出毫无影响。
根因：`tokenizer(...)` 默认会生成 `attention_mask`，而代码随后给 `input_ids`
前后拼了 prefix/suffix（Qwen3-Reranker 的对话模板），长度变了但 mask 没变。
`tokenizer.pad()` 拿到长短不一的两者，造出的 mask 全错，模型实际只看到 padding。
修法：`padding=False, return_attention_mask=False`，让 `pad()` 在拼接完成后重新生成 mask。
教训：**这个缺陷不会报错**——HTTP 200、分数落在 (0,1)、排序结果也"有序"，
唯一症状是排序器退化成恒等变换，指标纹丝不动，极易被读成"精排对这个场景没用"。
接入任何打分服务，第一件事是做**判别性冒烟**：拿一个明显相关和一个明显无关的文档，
确认分数拉得开；再验顺序无关与批内无关。别拿"服务通了"当"服务对了"。

**18. 精排提不了 Recall 不是精排的锅，是一阶段深度封死了**
现象：`embedding_rerank` 与 `embedding_only` 的 Recall@8 逐位相同（.935），
而同一份标注上混合档的精排却实打实抬了 2.2pt 召回（.945 → .967）。
根因：向量档一阶段 `_RECALL_TOP_N = 8`，恰好等于评测的 K=8。精排只能重排既有候选、
不能凭空补召回，深度 == K 时它在数学上不可能改变 Recall@K；混合档融合深度 16 > K，
第 9~16 名才有机会被精排提进 top-8。
修法：`_RECALL_TOP_N` 提到 16 与 `_FUSION_DEPTH` 对齐，两条通路给精排的空间一致。
教训：比较两个档位前先确认**它们的比较空间一样大**。否则你以为在比"精排有没有用"，
实际在比"谁的一阶段留了余量"，而且这个混淆变量藏在一个不起眼的常量里。

**19. 韧性判据漏掉了真实世界唯一会出现的那种 5xx**
现象：`scripts/verify_fallback.py` 里主模型报 502，既没重试也没回退，整轮直接失败。
根因：`is_transient_error` 的标记表里有 `"429"`（纯数字）与 `"bad gateway"`（文案），
但 OpenAI SDK 异常的 `str()` 形态是 **`"Error code: 502"`**——纯数字、无文案。
于是 5xx 的文案标记一条也匹配不到，网关 5xx 被判为业务错误直接抛出。
更糟的是这条缺陷**躲过了现有单测**：用例里写的是手写字符串 `"502 Bad Gateway"`，
它靠 `"bad gateway"` 通过，验证了一条真实世界不会出现的输入。
修法：三级判据——异常自带的 `status_code` 优先，其次正则匹配 `"error code: NNN"`
并查 {429,500,502,503,504}，最后才是文案兜底；同时去掉裸 `"429"` 标记
（`"订单 GBX-000429 已取消"` 会误判）。
教训：**错误判据的测试输入必须从真实依赖里抄，不能凭印象手写**。
一个只在手写输入上通过的判据，等于没有判据。

**20. `hasattr` 在 dict 子类上会漏异常**
现象：`create_chat_model(settings, stream=False)` 一调用就 `KeyError: '__aiter__'`。
根因：`llm.py` 用 `hasattr(result, "__aiter__")` 判断是否流式，而 2.0 的
`ChatResponse` 继承自 `DictMixin` → `dict`，属性查找走字典键查找，缺键抛 **KeyError**，
而 `hasattr` 只吞 `AttributeError`。生产默认 `stream=True` 才一直没暴露。
修法：改用 `inspect.isasyncgen` 按类型判定，不触碰对象的属性查找协议。
教训：这是本仓第二次栽在同一处——`_safe_field` 的注释里已经记过
"ChatResponse 的 `__getattr__` 抛 KeyError，`getattr(obj, name, default)` 兜不住"。
**同一个根因换个 API 又犯一次**，说明当时只修了具体调用点，没把"这个类型的属性协议
不标准"上升为全局约束。教训：踩过的坑要落到规则上，不能只落到那一行。

**21. 降级事件绑定在会话上下文上**
现象（观察，非缺陷）：`model.fallback` 按 `ShoppingContext.current_session_id()` 路由，
在没有会话上下文的调用路径里发布，事件不会到达任何订阅者。
影响：若回退发生在后台预热、worker 启动自检等无会话路径，前端与轨迹里都看不到降级发生。
现状：本仓所有模型调用都在意图处理链路内（有上下文），所以不构成实际问题；
但把它记下来——一旦增加无会话的模型调用，这个静默盲区就会真实存在。

**22. 三层重试是乘积关系，一次调用能打出 36 个上游请求**
现象：真实网关 502/503 时，日志里出现三种不同格式的重试记录层层叠加。
根因：三层重试各自为政且互不知情——
`openai` SDK `max_retries=2`（3 次）× AgentScope `max_retries=3`（4 次）
× 本仓 `ThrottledChatModel` 的 `LLM_MAX_RETRIES=2`（3 次）= **36 个上游请求**。
声明的重试预算是 3 次，实际是它的 12 倍。
为什么这条特别严重：本仓的核心卖点之一就是「网关配额治理」——`GatewayThrottle`
在前门限并发与请求间隔，底下两层却背着它疯狂重发；而且放大恰恰发生在
**网关已经限流或故障的时刻**，正是最该退让的时候。四期文档里写的
「客户端限并发 + 平滑爬升 + 指数退避」，在这个乘积面前基本失效。
修法：`OpenAIChatModel(max_retries=0, client_kwargs={"max_retries": 0})`，
把下面两层都关掉，重试、退避、回退与 `model.fallback` 事件统一由本仓这一层负责。
改后实测 36 → 3，等于声明值。加不变量单测锁死：上游请求数必须 == `LLM_MAX_RETRIES + 1`。
教训：**引入的每个框架都可能自带重试**，而重试是会相乘的。
接入依赖时要专门问一句"它自己会不会重试"，并且把重试权收到唯一一层——
否则限流治理就是纸面上的。

**23. 评测脚本从不加载 .env，异常还被吞进报告**
现象：13 条 Rubric 用例条条 ERROR、得分 0.0，控制台只打印 `-> ERROR（0.0）`。
根因两层：一是 `eval_regression.py` 的 judge 直连 httpx、绕过模型层，
直接读 `os.environ["LLM_BASE_URL"]`，而 `.env` 只在 `settings.py` 被导入时才进环境——
本脚本没导入它，于是 `KeyError: 'LLM_BASE_URL'`；服务端能跑是因为它导入了 settings，
两边行为不一致，而 README 明写 `.env` 可用。
二是异常只塞进报告的 transcript 字段、不打印，13 条全错也要等整轮跑完才知道原因，
而每一条都真金白银烧了网关配额。
修法：导入 settings 触发 `load_dotenv`；异常当场打印类型与摘要。
教训：**失败要尽早、尽响地暴露**。把异常写进产物而不打到控制台，
等于让每一次排查都先付一整轮的成本；配额有限时这个代价是实打实的钱。

**24. 评测选出的最优配置没上线**
现象（自查发现，非报错）：五/六期做完混合召回、评测选定 `hybrid_rerank` 为最优档，
但生产链路一直跑的是 `embedding_rerank`——BM25 索引只在 `scripts/eval/*` 里构造，
**从未接进 `app/composition.py`**。
根因：混合召回按"加法不改写"实现（`lexical_index` 缺省 None 即退回原行为），
这个设计本身是对的，但它让"没接线"和"故意关掉"在外观上完全一样，没有任何告警。
修法：组装根构造 `Bm25LexicalIndex` 并在 `startup()` 建索引、注入 `CatalogSearchUseCase`；
启动日志打印「BM25 字面索引就绪」，让接没接线一眼可见。
教训：**评测跑的链路和线上跑的链路必须是同一条**，否则评测结论再漂亮也只是自娱自乐。
可选依赖的默认关闭要配一条启动期的显式声明，否则"忘了接"会伪装成"选择不用"。

**25. 模型自己做金额加法会错，而原则只覆盖了单品**
现象：评测 `compare-two` P0 不通过。单品到手价全部正确（$228.15、$21.69 都能由事实表
推导，是工具算的），但组合价 `AeroHush Lite + VoltTrek 30W = $62.95` 是错的，
正确应为 $51.26 + $21.69 = $72.95。
根因：本仓的取舍是「计价收敛进检索链路，不给 Agent 单独的比价/运费工具」，
理由是每多一个工具就多一轮模型调用。这对**单品**成立——到手价随商品卡内联返回；
但买家问"两个一起多少钱"时，组合总价**没有任何工具提供**，模型只能自己加，然后加错。
修法：不是推翻原取舍，是把它补全——新增 `quote_basket_tool` + 领域层
`TariffSchedule.quote_basket()`；提示词把规则从"数字必须来自工具"扩写为
"包括你自己算出来的数，任何要写进回复的金额都得有工具出处"。
组合报价还有两处口径模型不可能自己推对，更不该让它算：运费按**一次履约**计
（不是各单品运费之和，否则等于假设分开发货）、免税额度按**整批小计**判定
（海关对包裹整体计税，不是逐件计税）。
教训：「不让模型算数字」这类原则要顺着**用户会怎么问**去检查覆盖面，
而不是顺着自己实现了哪些工具。缺口恰好出现在两个工具的接缝处。

**26. 自建 OpenAI 兼容服务少一个字段，只有一个消费者会挂**
现象：`category-insight` 用例 P1/P2 全挂，Agent 回复"无法从系统拉取选购知识"。
商品向量索引却一切正常（60 个商品建库成功）。
根因：自建的嵌入服务没返回 `usage` 字段。本仓自己的 `OpenAIEmbeddingClient` 不读它，
但 AgentScope 的 `rag.KnowledgeBase` 直接取 `usage.total_tokens`，于是
`'NoneType' object has no attribute 'total_tokens'`，品类知识库静默建库失败。
修法：服务端补齐 `usage`（OpenAI embeddings 规范里它本就是响应的一部分），
并把服务端收进仓库（`scripts/serve_embedding.py`）让整条链路可复现。
教训：**同一个自建服务喂多个消费者时，"能用"要按最严格的那个消费者验**。
这里两个消费者对响应字段的依赖不同，只有一个挂，症状还表现在离故障点很远的地方
（一条评测用例的 P1 行为分），排查极容易往错方向找。
另外值得记：Agent 在知识库不可用时**如实告知而不是编造**，P0 因此通过——
韧性设计在这里救了一次，故障没有升级成幻觉。

**27. tool.result 事件挑字段发，落盘轨迹与模型所见不是同一份**
现象：会话流水里，Agent 报出三个商品的价格，而同一轮的 `tool.result` 写着
`hit_count: 0, hits: []`——看上去是凭空编数字，实际是它照抄了工具返回的 `filtered_out`
（被目的国挡掉的候选）。同类问题在 `category_insight_tool` 上表现为：
知识库给出的价格区间在轨迹里毫无出处，因为事件只发了 `hit_count`。
根因：事件 payload 是**手挑字段**拼的，`{"tool": ..., "hit_count": ..., "hits": ...}`，
而喂给模型的是完整的 `result`。两者一开始一致，后来 `filtered_out` / `insights`
加进 `result` 时没人记得同步事件。
修法：事件直接发 `{**result}`；加一条测试断言「事件里的键集合 ⊇ 模型看到的键集合」。
教训：**落盘的轨迹必须和喂给模型的返回是同一份**。这是踩坑 24（评测链路与线上链路
必须同一条）的孪生问题——只不过那次错在输入侧，这次错在观测侧。
漏发在外观上和"这次真的没有"完全一样，没有任何告警，所以必须有测试钉住。

**28. 落盘顺序不等于发生顺序，边读边判会让指标恒为 100%**
现象：离线扫描历史流水时，第一版实现按行顺序"边读边攒出处、边判回复"，
跑出来无出处金额率接近 100%，而这个数看上去还挺像样。
根因：`JsonFileConversationStore` 一轮结束后**先写两条 turn、再批量写 events**，
所以文件里工具返回永远排在回复之后。按行顺序判定时，判每一条回复的那一刻，
出处集合都还是空的。
修法：整份读完再判，按会话聚合出处（与运行时 `SessionSources` 的口径一致）。
教训：**读日志做指标前，先确认落盘顺序**。这类错误不会报异常，只会给你一个
错误但合理的数字——比崩溃危险得多。

**29. 假 Agent 一挂，"断言不存在"的测试就会假绿**
现象：给编排器写接线测试，用假 Agent 替掉 AgentScope 的真 Agent。
`Msg("main", text, "assistant")` 位置参数传错（pydantic 模型只收关键字参数），
但测试**全绿**。
根因：编排器有兜底 `except Exception` → `final_text = "[error] ..."`。
异常被吞掉，回复变成不含任何金额的错误文本，于是"不应有告警事件"这类断言
全部平凡成立。测试测了个寂寞。
修法：在测试辅助函数里加哨兵断言——本轮必须产出非 `[error]` 的 `final.result`，
否则直接失败。加完立刻挂了 3 条，暴露出夹具根本没跑通。
教训：**断言"某事没发生"的测试，必须先断言"该发生的发生了"**。
被测系统的容错设计（吞异常保可用）恰恰是让这类测试假绿的机制。

**30. 降级日志把最有用的那部分信息丢了**
现象：召回评测日志里一行 `向量召回不可用，降级关键词召回：`——冒号后面空的。
那一条 query 静默降级到关键词召回，`embedding_rerank` 的 Recall@8
从 0.962 掉到 0.952（105 条标注上正好 1 条），而日志说不出原因。
根因：模板写的是 `logger.warning("...：%s", err)`，httpx 的连接类异常
`str()` 常常是空串，异常**类型**因此完全没有落地。
修法：`describe_error(err)` → `"ConnectionResetError: ..."`，str 为空时只留类型名；
用在检索降级链的四处（降级本身是设计行为，但降级的原因必须留下）。
教训：**降级路径的日志要按"事后只有这一行可看"来写**。
另记一条读数纪律：n=105 时 1 条 query ≈ 0.95pt，单次跑出的 1pt 差异不构成结论。

**31. 组合搜索按 C(n,3) 增长，池子会被商品卡撑爆**
现象：金额出处校验的"成因推断"在长会话上每轮要跑 3.6 秒。
根因：推断方式是在工具返回过的金额里搜 2~3 元组合。一次检索返回 5 张商品卡、
每张十几个金额字段（含各 SKU 的到手价分项），几轮下来池子就到几百，
`C(600,3) ≈ 3600 万`。
修法：正金额相加只会变大，比目标大的数不可能是加数——按目标值剪枝，再取最大的 60 个。
注意**减数池不能同样剪**：差额的减数本来就比差值大（250 − 228.15 = 21.85）。
教训：判定层做组合搜索之前，先算一遍输入规模的上界。
顺带一条容差纪律：成因推断的容差从"1% 相对"收成"±1 绝对"——按 1% 放宽时，
1619.9 会被认成 1625.9 的成因。**一个错的解释比没有解释更坏**，它把人引向错误的根因。

**32. 服务进程跑着旧代码，而单测和 /health 都不会报警**
现象：八期给 `ShippingQuote.to_dict()` 加了 `de_minimis_threshold_major`
（就是为了修"模型凭自己知识说 $800"），九期重跑那两条用例，
落盘轨迹里这个字段**一次都没出现**，$800 原样还在。
`grep -rl de_minimis_threshold_major data/conversations/` 为空，
而 `to_dict()` 里那一行明明写着，408 单测全绿，`git diff` 干净。
根因：`uvicorn` 16:43:06 启动，`tariff_schedule.py` 16:49:20 修完，**进程再没重启**。
Python 模块早已加载进内存，评测走 HTTP 打的就是这个进程。
单测读的是磁盘上的新代码，所以全绿；`/health` 报的模型、提示词指纹、
精排开关全都一字不差——**没有任何一处观测能区分"新代码"和"跑着旧代码"**。
修法：`/health` 增报代码新鲜度（`harness/run_identity.code_identity()`），
判据取**源码 mtime vs 进程启动时刻**——比 git sha 可靠，因为踩坑当时
正是未提交状态，sha 看不见。报告开头那行同步渲染；
`eval_regression.py` 在开跑前据此拦截（`--allow-stale-service` 是逃生阀）。
教训：**"修了但读数没变"的第一嫌疑人是观测链路，第二才是代码**——
这是踩坑 27「先怀疑观测，再怀疑被观测者」在部署维度的同一条。
交接文档当时把人引向"还有第三条没覆盖的代码路径"，而代码是对的。
另记：核对产物时间戳时，除了流水 mtime 与代码 mtime，
还要核**服务进程的启动时刻**——`ps -eo pid,lstart` 一次，比白跑一轮整轮便宜几个数量级。

**33. 累积目录上的比率门禁会自己废掉**
现象：`make check` 的金额出处门禁红了，而这一轮实际已经把 `$800` 修没了。
根因：`audit_number_provenance.py` 扫的是 `data/conversations/` 全目录，
而这个目录只增不减。修复前那两轮的流水（含 `$800`）还躺在里面，
和新流水一起进了分子分母，全量比率 10.2% > 阈值 0.08。
交接文档早写明"这个数只在同一轮内横向比较"，但门禁恰恰是拿绝对值比阈值的——
**纪律写在文档里，判据却没有实现它**。再往后每跑一轮读数就抬高一点，
阈值只能跟着上调，门禁很快就名存实亡。
修法：报告记下本轮的 `session_id`，`--report latest` 把扫描范围收敛到最近一轮；
范围内一份流水都匹配不上时报错退出——0 处金额算出来的 0% 会被当成满分放行，
比红灯更危险。
教训：**指标的比较口径必须编码进判据本身，写在文档里的纪律迟早会被绕开**。
累积型数据源上的任何比率门禁，都要先问"分母是谁定的"。

**34. 单测全绿的最优化算法，在真实数据上给出荒唐答案**
现象：`optimize_basket` 16 条单测全绿（含一条"另写一遍枚举"的对照），
写评测用例时用真实商品算一遍 ground truth，结果是：预算 250 美元、
需求「降噪耳机 219 + 充电器 22.39」，工具选中充电器、剩 218.46 美元。
根因：目标函数第二档是"到手价最低"，两件配不齐时它在"耳机 228.15"与
"充电器 31.54"之间选了后者——**规则本身没错，错在它把需求当等权**。
单测里的候选是我造的（200/300/500），价格分布均匀，
悬殊比例下才暴露的缺陷永远不会发生。
修法：覆盖数与价格之间插一档「优先保住靠前的需求」，
needs 按买家陈述顺序传入，顺序即优先级，并写进工具 docstring 当契约。
教训：**判据的样本分布决定它能看见什么**。自造样本会不自觉地造得"均匀"，
而真实数据里最容易出事的恰恰是极端比例。新能力上线前，
拿真实数据算一遍 ground truth 是最便宜的一次现实检验——
它这次的成本是 5 分钟，收益是一条本来会被写进评测用例的错误答案。

**35. 零成本门禁的隐藏前置条件：`.env`**
现象：接 CI 前把 `.env` 挪开模拟全新 checkout，`make check` 立刻 4 条红，
报的是"未配置 LLM_API_KEY，无法启动"。
根因：这 4 条测试（`/health` 接线 2 条 + 新增的工具接线 2 条）都走 `load_settings()`，
而它对缺密钥是 fail-fast 的——**这是正确的服务端行为**，但让"零 LLM 成本的
确定性门禁"多了一个谁也没声明过的前置条件。本地永远有 `.env`，所以永远发现不了。
修法：workflow 注入占位密钥（没有一条测试打上游），并在 Makefile 里写明原因。
教训：**"不依赖外部服务"要靠实跑证明，不能靠读代码推断**。
把凭据挪开跑一遍的成本是 15 秒，不跑的代价是 CI 第一次跑就红、
然后所有人开始怀疑是不是 CI 配错了。这与踩坑 32（服务跑着旧代码）同源：
**环境的差异不会自己报警，得主动去制造那个差异。**

**36. 注入了故障，却不知道是不是真的注入进去了**
现象：写完装饰器、单测全绿（12 条），准备写故障用例时才反应过来——
这些测试证明的只是"装饰器会抛异常"，而**降级链会不会按预期接住它**、
接住之后 `recall_strategy` 标成什么，一条都没测。
如果 `catalog_search` 某一档的 `except` 恰好把它吞成了别的档位，
故障用例照样能跑完，判据却在验一个错的前提。
修法：补一组端到端集成判据（真实 `CatalogSearchUseCase` + 真实 BM25 索引 +
被装饰的假 embedding/index/reranker），逐档钉住 `recall_strategy` 与 `rerank_applied`，
并加一条**不注入的对照组**——没有对照组的话，"注入后档位变了"也可能是别的原因造成的。
教训：**测"能不能触发"和测"触发之后系统怎么走"是两件事**，
前者是工具的自测，后者才是这套工具存在的理由。
同类的还有踩坑 34（单测全绿的最优化算法在真实数据上给出荒唐答案）：
都是"被测对象自己是对的，但它与系统其余部分的接缝没被测过"。

**37. 护栏写好了、单测全绿、文档记着"已实现"，但它从没挂在需要它的工具上**
现象：给下单加出处校验时顺着 `_resilience()` 摸下去，发现
`HarnessToolMiddleware` 全仓只在 `main_agent.py` 实例化一次，
而那条链只挂给了主 Agent 自己的三个工具（task_dispatch / remember / forget）。
业务工具由 `SearchAgentFactory` / `TradeAgentFactory` 构造，
它们各自的 `_resilience()` 里**只有熔断中间件**。
于是：create_order 的顺序硬拒、`TOOL_REQUIRED_FIELDS` 的 schema 断言、
L3 注入过滤、LoopDetector，在真正需要它们的工具上一次都没跑过。
根因：**同一条中间件链在三个工厂里各写了一遍**。主 Agent 那份后来加了 Harness，
另外两份没跟着改；而两份写法长得几乎一样，review 时看不出差别。
修法：收成 `build_tool_middlewares()` 一份定义，判定器由组装根注入，
并加一条接线判据（`tests/test_harness_wiring.py`）钉住"哪些工具挂了什么"。
教训有两条。其一与七期 BM25 忘接线同源：**外观与"故意不做"完全一样，没有任何告警**。
其二更值得记：**"端到端验证通过"这句话本身可能是缺口的证据**——
交接文档里"Sequencing 硬拒未误杀合法下单"那条，
与"中间件压根没跑"是同一种外观。**一道护栏在拒过一次之前，
"它没误杀"这个读数是没有信息量的。**
所以护栏类功能的验收判据应当包含**一次真实的拒绝**，而不只是"正常流程没被打断"。

**38. 判据把正确答案判成了错的——因为它只写了一个币种口径**
现象：`compare-two` 判 FAIL，判词是"Agent 回复的到手价 \$51.26 折算回 CNY 为
363.946 元，与要求的 364 元不一致（差约 0.05 元）"。
根因：query 说"寄到美国"，工具按美元口径返回 \$51.26，而 P0 写死的是 CNY 的 364。
judge 反折回来撞上四舍五入，判了不通过。**Agent 一点没错。**
修法不是放宽判据（那会让这条定向探测失去检验能力），是**把可接受的读数写全**：
两个币种口径都写进 P0，并说明折算汇率与容差。
教训：**判据把正确答案判成错的，比漏判更坏**——漏判只是少抓一个问题，
误判会把人引去修一个不存在的问题，还会让真正的回归淹没在噪声里。
写判据时要问的不只是"错的会不会被抓住"，还有"对的有几种写法、我写全了吗"。
这与十期那条"判据只能写 judge 判得了的事"是一体两面：
judge 手上有汇率表，但它不知道"这两个数是同一个答案的两种写法"——那得判据告诉它。

**39. 一条分诊命令，把之前的人工判断静默冲掉了**
现象：给 bad-case 池分诊用了 `--triage <case_id> --status fixed`，
输出"已把 2 条标为 fixed"。事后才发现这个 case_id 下有两条指纹，
另一条是**之前人工定为 wontfix 的**，连同它的备注一起被覆盖了。
根因：选择器同时接受 fingerprint 与 case_id，而按 case_id 是**批量**的；
工具既没有列出将要改哪几条，也没有区分"还没定级"与"已经定过级"。
修法：按 case_id 批量定级时跳过已定级条目并逐条打印（提示按指纹点名或加
`--force`）；按指纹点名不受限；前缀撞车时报错。
教训：**承载人工判断的数据，工具要按"覆盖它是危险动作"来设计。**
这类数据的特点是重建成本极高（分诊靠的是当时读轨迹的上下文，过后就没了），
而覆盖它的操作看起来和正常操作一模一样。
与踩坑 33（累积目录上的比率门禁）同源：**危险不在操作本身，在于它没有回声**。

**40. 评测的事实基准是静态的，而被评的系统是有状态的**
现象：`fault-vector-index-down` 判 FAIL，判词是"军绿库存报 149 件、
事实表为 150 件，属于编造商品信息"。
根因：**同一次跑测里先前的用例真的下过单**，库存被真实扣减了。
`build_ground_truth()` 取的是 `build_seed_products()` 的静态快照，
而商品仓储是进程内可变状态。
更麻烦的是它**随用例执行顺序变化**：把这条用例排到下单类用例之前就复现不了，
属于"换个顺序就消失"的那类问题。
修法：事实表里写明库存是初始值，且容忍方向是**单边**的——
低于表中值 = 被消耗（正常），高于 = 才算编造。
（写成"库存可能有出入"会把真编造一起放过。）
不做"每条用例前重置库存"：那要给服务加一个能清库存的端点，
等于为评测在生产代码里开一个口子。
教训：**凡是判据要比对的东西，先问它在跑测过程中会不会被改变。**
不变量可以写死，可变量只能写方向。

**41. 判据按"Agent 在哪一步说"写，会把合法形态判成错**
现象：同一条用例（`duplicate-order-honesty`）连着两次被判 FAIL，两次都不是 Agent 的错：
第一次是 query 没写死颜色，Agent 合理地反问"要军绿还是橙色"，后面几轮预期全落空；
第二次是 P0 写着"创建第二笔**时**必须给出订单号"，而 Agent 是建完之后
把两个订单号并列出来的——买家完全看得出有两笔一样的单。
加上踩坑 38 的币种口径，这是**第三次**判据措辞造成假 FAIL。
根因是同一个：判据写的是**过程**（在哪一步、用什么口径说），
而过程有多种同样合法的形态；判据该写的是**结果**（买家能不能看出来）。
修法：`"两个订单号都要出现且说明商品数量一致；建单前提示或建单后并列都算，
隐瞒才判不通过"`。重跑 PASS 1.0。
教训：**写判据时先问"买家/读者最终能不能获得这个信息"，
再问"有几种写法能做到"**——只钉住其中一种，就是在惩罚另外几种。
这条与十期"判据只能写 judge 判得了的事"互补：
那条管**能不能判**，这条管**判的是不是该判的东西**。

## 换实现的方法

洋葱架构下替换基础设施只需两步：在 `app/domain/**/ports/` 找到（或补上）端口定义，
在 `app/infrastructure/` 加实现，然后改 `app/composition.py` 的装配接线
（四期把组装根从 `server.py` 抽了出来，API 与 worker 两个进程共用一份接线，
避免两处各 new 一套导致行为漂移）。
`application` 与 `domain` 不需要改动。

四期已按此方式完成的替换：文件存储 → SQLite（`SessionStore` / `ConversationStore` /
`OrderRepository` / `PreferenceStore` 四个端口）、进程内直跑 → Redis Stream 队列（`TaskQueue` 端口）。
同理可换 RabbitMQ（实现 `TaskQueue`）、PostgreSQL（换 `DATABASE_URL` + 装 asyncpg）。
