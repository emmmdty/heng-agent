## 〇、开工的前 20 分钟：又是纯本地问题

交接文档写着"九成情况下服务器是好的，只是隧道没起"。这次连隧道都不是：

```
ssh -o BatchMode=yes gpu-5090 hostname   → Host key verification failed
cpolar-ssh-update                        → ssh config already up-to-date（端口没变）
ssh-keygen -R '[29.tcp.cpolar.top]:10857' → not found in known_hosts
```

**known_hosts 里压根没有这台机器的条目**，而 `BatchMode=yes` 遇到未知 host key
不会问、直接失败。远端两个服务分别跑了 23 小时和 21 小时，一直好着。

代价 20 分钟。这是踩坑 12（代理把"没人监听"伪装成 502）的**同族**：
**探活失败的第一步永远是分层——连不上 / 连上了但握手失败 / 握手了但对面报错**，
三层的修法完全不同，而三层的外观都是"连不上服务器"。

## 一、缺陷 1：`clarify-missing-address` 编造买家的收货地址

### 事实

买家原话只有"帮我下单 2 个 LumenGo 露营灯军绿色。"，Agent 回复：

    **收货地址**：您之前的记录是上海市浦东新区世纪大道100号，这次还是这个地址吗？

轨迹（`eval-clarify-missing-address-7cd301.jsonl`）里本轮只调用过
`product_search_tool`，没有任何工具返回过地址；`data/preferences/` 里也没有
——排除了踩坑 40 那种"跨用例状态泄漏被误判成编造"。**它就是编的**，
还给编出来的东西安了一个"您之前的记录"的出处。

### 决策 1：走确定性判据，不走提示词

交接文档已经定了方向，本期只是执行。理由复述一遍是因为它是本仓最稳的一条线：

- 此前四轮该用例都 PASS（1.0 / 0.825 / 1.0 / 1.0），**频率未知**。
  靠 judge 抽查等于靠运气。
- 1.0 → 0.75 的落差正好落在自然波动带（单条 0.35）里，方差解释得掉；
  但"编造了一个收货地址"是"发生了没有"，不是"高了低了"（踩坑 45）。

落点：`app/application/harness/contact_provenance.py`，轮末校验回复里的
地址 / 电话 / 邮编能否在工具返回或买家原话里找到出处，命中发 `contact.unsourced`。

### 决策 2：判据范围刻意收窄，**不认收件人姓名**

方向一律取"宁可漏报不误报"（同金额出处校验）。具体六条收窄都写在模块 docstring 里，
这里只挑最反直觉的一条说明：

**不认收件人姓名。** rubric 的 P0 明明写着"不得编造收货人"，但中文姓名与品牌名、
商品文案在字面上无法区分，任何识别规则都会把"张伟同款"这类文案判成编造。
**这是有意留下的缺口，不要补**——一个会误报的判据，最终会让人把整条判据关掉。

同理：碎片式地址（"寄到上海"）不认，裸六位数邮编不认，地址里不允许空格。

### 决策 3：比对只取"门牌核心"

买家写"浦东世纪大道100号"、Agent 补全成"上海市浦东新区世纪大道100号"是**正常行为**，
按全串比对会把它判成编造。所以只比最后一个行政区划标记之后的部分。

实现上还有一个中文特有的坑：中文没有词边界，`[一-龥]{2,4}(?:市)` 会从"是上海市"
起匹配，把前一句话的尾字吞进来。修法是把匹配起点逐位右移、取仍能匹配的最后一个
位置（`_shortest_address_span`）。

### 决策 4：从落地第一天就带下游（二十期的教训）

二十期查明 `arith.inconsistent` 在 app 之外**零消费方**，判据"在真实评测里等价于不存在"。
所以 `contact.unsourced` 不允许重蹈：同一次提交里落地
`scripts/eval/audit_contact_provenance.py`，进 `make check` 成为第六项。

**门禁口径同算式自洽、与金额出处不同：不设阈值、不设样本量下限，命中一处即红。**

| 判据 | 口径 | 为什么 |
|---|---|---|
| 无出处金额率 | `--max-ratio 0.08` + 样本量下限 | 比率指标，修辞取整本来就占几个点 |
| 算式自洽 | 1 处即红 | 事实错误，能指着原文说"这一行算错了" |
| **收货字段** | **1 处即红** | 事实错误，能指着原文说"这个地址不存在" |

### 验收证据：护栏必须真红过一次

交接文档五之二："只有一个证据算数——它拒绝过一次，而且那次拒绝被记了下来。"

```
$ uv run python scripts/eval/audit_contact_provenance.py --gate
会话 111 个（1 个有发现，0 个在运行时就已告警）｜断言 34 处｜无出处 1 处

## eval-clarify-missing-address-7cd301（1/1，本次补判发现）
  - [address] 上海市浦东新区世纪大道100号
  买家原话：帮我下单 2 个 LumenGo 露营灯军绿色。
$ echo $?
1
```

**111 份历史流水、34 处断言、零误报**——另外 33 处是买家在用例里自己给的
`13800000000` / `310000`，全部判为有出处。

**注意本期的定向重跑 PASS 1.0 不能当证据**：那轮 Agent 根本没有编造，
护栏没有被检验到（经验 3 / 踩坑 42 的同一条）。真正的证据是上面那次红。

## 二、缺陷 2：`conflict-budget-spec` 把不具备的属性说成具备

### 事实

买家："预算 200 元，给我来一副顶配的主动降噪耳机。"
Agent 把 `AeroHush Lite`（半入耳、只有通话降噪、¥299）列在
"库里有的主动降噪耳机"这个标题下，暗示加 99 元就能买到 ANC。

七轮历史：`PASS PASS PASS FAIL FAIL PASS FAIL`——**间歇性，不是稳定复现**。

### 决策 5：不动召回，动工具返回的结构

前两次修都在动召回，都没拦住：

| 期 | 修法 | 结果 |
|---|---|---|
| 十九 | "无主动降噪 ANC" 写进 description | **帮了倒忙**：BM25 不理解否定，看见词就命中，召回反而更强（踩坑 46） |
| 十九 | 改成不可检索的 highlight | 字面路压下去了（BM25 3.035 < 门限 4.0），**向量路照样召回**（读数纪律 4） |

第三种修法的依据是**四次成功先例的共同点**：`filtered_out`、`combine_hint`、
`ship_to_unsupported`、`taxable_base_major` 给的都是**结构化字段**；
而卡片上那句"仅通话降噪（麦克风侧），无主动降噪 ANC"是**散文**，模型可以不当回事。

落点：`ProductHighlight.negates` 把"不具备什么"从散文升级成结构化声明；
命中买家 query 时商品卡带

```json
"attribute_mismatch": {
  "missing": ["主动降噪"],
  "note": "买家点名要的「主动降噪」，本商品**明确不具备**。不得把它列为具备该属性的候选，也不得暗示加价/换规格就能获得；要推荐它，必须同时说明它不具备主动降噪。"
}
```

### 决策 6：声明挂在写着那句否定的 highlight 上，不另开商品级清单

两份清单迟早会脱钩，而**脱钩的外观是"判据没生效"**——本仓栽过的
docstring 与规则表脱钩（十期）、判据与规则表脱钩（二十期，错了九期）是同一形状。

### 决策 7：`note` 里带"该怎么办"，不只是"是什么"

十期那次，模型拿着一句"这些商品不发欧盟"直接告诉了买家。
工具的错误信息要能让模型自纠——这是五之二里"另外两条要想一遍"的第二条。

### 决策 8：**不改提示词**

交接文档明确写着"不要再改提示词：提示词已经拦过两次没拦住"。
更重要的是**归因**：同时改两处，下一轮就说不清是哪一处起的作用。

### 验收证据：待测行为真的发生过

定向重跑 PASS 1.0，但**一次 PASS 不是证据**（读数纪律 3），
而且要先排除"这回没触发"（经验 3）。查轨迹：

```
召回： ['P1004', 'P1023', 'P1022', 'P1053', ...] | 档位 hybrid_rerank
✔ 命中 attribute_mismatch: P1022 AeroHush Lite 半入耳蓝牙耳机 ['主动降噪']
```

**跑在 `hybrid_rerank`（正常态）上，P1022 确实被召回了，卡片上确实带着那个字段**
——不是"这回没召回所以没出错"。这条同时满足了读数纪律 4（不能只在字面路上验证）。

连跑三轮的读数见第四节。

## 三、决策 9：轨迹保真单独钉一条

`attribute_mismatch` 藏在 `hits[]` 里，而 `test_event_carries_same_keys_as_model_sees`
只比**顶层** key，看不见它。经验 2 的原话是"落盘的轨迹必须和喂给模型的返回是同一份"，
`filtered_out` 与 `insights` 当年都是"后来加进返回值、忘了同步事件"。

补的这条测试**第一次跑就是绿的**（现有实现本来就发全量 `hits`），
所以它不是 TDD 意义上的"先红后绿"，而是一条**回归钉**——
它的价值在于下一个往卡片里加字段的人不会静默地破坏轨迹保真。
这一点如实记在这里，不要在别处把它记成"修好了一个缺陷"。
