# 十一期实施计划与决策

本轮由 Agent 自主规划、自主决策并执行，本文件是**决策记录**：每条决策写清
「做什么 / 为什么这么做 / 放弃了什么」，便于事后追责与回滚。

范围来自 `交接文档.md` 第五节的排序，选中的是**主线三① + 十期挖出的两个字段缺陷 + 主线二剩下的 CI**，
合称「工具补全三件套」。三项的共同性质：**判据是确定性算出来的，不需要 LLM judge**，
所以本轮全程零 LLM 成本、可反复复现。

基线（开工时实测）：`uv run pytest -q` → **462 passed**；十期成果已提交为 `fcec22d`。

---

## 一、为什么是这三项，而不是主线一或先跑基线

| 候选 | 结论 | 理由 |
|---|---|---|
| 主线三①「预算感知组合优化」 | **做** | 交接文档指定的下一轮主线；60 SPU 候选空间可暴力枚举出真最优解，ground truth 确定性可算，不欠 judge 一分钱 |
| 十期缺陷 1/2（`taxable_base` / 免税额度原生口径） | **做** | 判据（金额出处校验）**已经在报**这两处：`€3.72` 与 `$800`。「判据指的地方就是工具该补的地方」，改字段比改提示词更可能奏效 |
| 主线二 CI | **做** | `make check` 已经有了，接 CI 是一个 workflow 的工作量；不接就永远是"提交前记得跑" |
| 主线一（用例 28→40+） | 缓 | 验收标准是"整轮均分掉进 0.75~0.9"，必须跑真实评测才能验收；本轮无人值守，不烧网关配额 |
| 先跑 `make eval` 立基线 | 缓 | 需两条隧道 + Qdrant/Redis 在线且 60-90 分钟真实成本；留给有人值守时做 |

放弃的选项：**不动检索参数、不动提示词里的规则条款**——十期改了 `build_ground_truth()`，
judge 判别力已变，十期前的分数不可比；在拿到新基线之前调参数是拿噪声当信号。

## 二、逐项决策

### 决策 1：`taxable_base_major` —— 给"应税基数"一个出处

十期实测缺陷：Agent 解释关税时写「1,199 × 12% ≈ ¥3.48」，**最终数字对（工具给的）、
计税基数错**（正确基数是超出免税额度的 3.72，不是整单 1199）。同一轮出处校验报了两处
无出处金额，都是 `€3.72`——正是它自己减出来的应税基数。

- **做法**：`ShippingQuote` / `BasketQuote` 的 `to_dict()` 增 `taxable_base_major`
  （超出免税额度、实际参与计征的那部分，目标币种口径）。
- **不做**：不在提示词里加"计税基数是超出部分"的规则条款。理由同 `combine_hint`：
  隔着几千 token 的规则敌不过模型眼前正在读的那个数；**给它可抄的字段**比讲道理有效。
- **顺带**：`number_provenance._MONEY_FIELD` 增 `taxable`，让这个数进金额池，
  能参与成因推断（否则由它派生的差额只会被归成 `unsourced`，线索丢了）。

### 决策 2：免税额度补**原生口径**

规则表里 US 的额度本来就定义为 800 USD、EU 为 150 EUR，但存的是折算后的 CNY 分，
`de_minimis_threshold_major` 也只按 `target_currency` 回一个值。于是买家语境是美国、
目标币种是 CNY 时，Agent 要说"美国免税门槛"只能自己反折成 `$800`——**这个 `$800` 是第三次回来了**
（八期堵"凭知识说"、十期堵"工具没被调到"、这次是"调到了但口径不对"）。

- **做法**：常量从 `_DE_MINIMIS_CNY_MINOR: dict[str, int]` 改为
  `_DE_MINIMIS_NATIVE: dict[str, tuple[float, str]]`（金额 + 原生币种），CNY 口径由汇率表推导；
  `TariffSchedule` 暴露 `de_minimis_native()` / `de_minimis()` 两个公开方法；
  `to_dict()` 增 `de_minimis_threshold_native_major` + `de_minimis_threshold_native_currency`。
- **连带**：`taxable_base_native_major` 一并回传（原生币种口径的应税基数）。
  不加这条，"超出 €150 的部分是 €3.72"这句话里的 3.72 又会没有出处——
  与 `$800` 是同一条缝的另一端，一次封掉。
- **已知行为变更**：JP 免税额度从 500 CNY 变为 **480 CNY**。原值 `10_000 * 5` 用的是
  手写的 0.05 汇率，而汇率表里 JPY 是 0.048；改为从汇率表推导后消除了这处重复定义。
  这是**修正**而非退化，但属可观测的行为变化，故在此显式记录。
- **连带修改**：`scripts/eval_regression.py::_landed_price_rules()` 原先直接 import 私有常量，
  改为走公开方法，并让 judge 的规则表同时给出原生与 CNY 两个口径。

### 决策 3：`optimize_basket_tool` —— 预算感知的组合优化

现状：买家给了预算，Agent 只能一件件查、自己拼、自己减，"预算还剩 $22"这种数字
至今没有工具出处（判据里表现为 `suspected_difference`）。

**目标函数（字典序，刻意选可判定的口径）**：
1. 覆盖的需求组数最多；
2. 同覆盖数下**组合到手价最低**；
3. 仍并列时按 `product_id` 字典序取定——保证同输入同输出，可作回归基线。

- **为什么不按"评分/性价比"最优**：那要先定义一个价值模型，而价值模型无法确定性验证，
  ground truth 立刻退回给 judge 打分。**能拿回确定性判据的，就别留给 judge。**
- **接口形状**：入参 `groups`（每组 = 一个需求 + 候选 product_id 列表 + 件数）、
  `budget_major`、`ship_to`、`target_currency`。分组形状是刻意的：买家说"耳机 + 登机箱，预算 300"
  就是两个需求槽位，每槽最多选一件；用平铺的候选列表表达不了"这两个不能重复买"。
- **返回**：选中组合 + 完整 `BasketQuote` 报价 + `budget_major` / `remaining_major`
  + `uncovered_needs`（含该需求在预算内的最低到手价，让"再加 X 就能配上"也有出处）
  + `separate_purchase_landed_major` / `combining_saving_major`（分开买 vs 合并买的差额，
  正是判据一直在报的第二条缝）。
- **运费口径**：**必须**走 `quote_basket()` 的一次履约口径（首件全价 + 续件 60%），
  不能把单件到手价相加。这正是 `_to_card` 里 `combine_hint` 在防的事，新工具内部同样会踩，
  写单测钉死。
- **目的国校验顺序**：规则表支持性校验放在商品可达性**之前**（十期踩过：顺序反了会
  把"规则表没有 DE"报成"这些箱子不发欧盟"，模型无从自纠）。
- **枚举规模**：组数 ≤ 4、每组候选 ≤ 12，组合数上限 20000，超出即报可行动的错误。
  60 SPU 下典型规模是 3 组 × 8 候选 = 729 种，暴力枚举毫秒级。
- **不做**：不做多件同款的数量优化（"买几个最省"），不做跨需求替代推荐。YAGNI。

### 决策 4：CI 接 `make check`，但**排除**金额出处那一项

`make check` 四项里 `provenance` 扫的是 `data/conversations/`（gitignore、跑测产物），
CI 全新 checkout 上一份流水都没有，`--report latest` 会按设计报错退出。

- **做法**：新增 `make check-ci` = `test + datasets + cases`（三项纯静态、无外部依赖）；
  CI 调这一个目标。
- **不做**：不给 provenance 加"没数据就当通过"的旁路。**0 处金额算出来的 0% 被当成满分放行，
  比红灯更危险**（这条是十期踩坑 33 的同一个教训）。宁可在 CI 里明确少跑一项，
  也不要让一项判据在 CI 上变成永远绿的装饰。

### 决策 5：评测用例

新增 3 条覆盖新工具的用例，P0 数字全部由 `TariffSchedule` + 优化器**真算**一遍写死。
用例只入库、本轮不跑（无人值守不烧配额），静态自检 `audit_cases.py` 必须过。
实际落地的三条 id 是 `budget-optimize-fit`（smoke）/ `budget-optimize-shortfall` /
`budget-optimize-unshippable-candidate`——第三条是写用例时补的：
组合优化路径上"候选被排除"很容易被说成"没有这个商品"，与单品路径的
`conflict-unsupported-destination` 是同一类缺陷的两个入口。

## 四、执行中的偏离

### 偏离 1：目标函数加了一档「优先保住靠前的需求」（推翻决策 3 里的"需求等权"）

原设计写的是"需求之间等权，配不齐时取覆盖数最多、其次最便宜的那组，不做优先级推断"。
**写评测用例、拿真实商品实算的那一刻就露馅了**：

    预算 250 美元，需求「降噪耳机 219 美元 + 充电器 22.39 美元」，
    两件合计 256.04 超预算 → 同覆盖数取最便宜 → 配了个 31.54 美元的充电器，
    还剩 218.46 美元，买家最想要的耳机被丢掉。

这不是"另一种合理取舍"，是个荒唐答案。改法是在覆盖数与到手价之间插一档：
**needs 按买家陈述顺序传入，顺序即优先级**，配不齐时保住靠前的。
改完同一场景给出的是"耳机 228.15、还剩 21.85、充电器还差 6.04"——正是买家要的答案。

顺序作为**显式契约**写进工具 docstring（模型看不到领域层注释），
不是让工具去猜哪个需求更重要。

教训与十期那条同源：**能力做完不等于做对，要拿真实数据实算一遍**。
这个缺陷单测抓不到——单测里的候选是我自己造的，价格分布均匀，
只有真实商品库里"219 美元 vs 22 美元"这种悬殊比例才会把它逼出来。

### 偏离 2：多回一个 `additional_budget_needed_major`

原设计缺口只回"该需求单买的最低到手价"。写用例时发现买家真正问的是
**"再加多少能配上"**，而那个数既不是单买价、也不是"单买价 − 预算余额"：

    正确：把它并进组合重新报价 256.04 − 预算 250 = 6.04
    错误：单买价 31.54 − 余额 21.85 = 9.69（把组合运费当成了分开发货）

后者恰恰是模型自己减时会犯的错。既然判据要禁止模型自己算这个数，
就得把正确的那个给它——同 `combine_hint`、同 `de_minimis_threshold` 的思路。

### 偏离 3：schema 断言表补了 quote_basket_tool

原计划只给新工具加 schema 断言，实作时发现 `quote_basket_tool` 从来就不在
`TOOL_REQUIRED_FIELDS` 里（断言表是七期写的，后面加的工具没有回头补）。
一并补上，成本为零。

### 偏离 4：CI 里发现 `make check` 依赖 `LLM_API_KEY` 存在

接 CI 前把 `.env` 挪开模拟全新 checkout，`make check` 立刻 4 条红：
两条 `/health` 接线判据 + 本轮新增的两条工具接线判据都走 `load_settings()`，
而它对缺密钥是 fail-fast 的。**没有一条打上游**，只是构造不出 Settings。
处理：workflow 注入占位密钥，并在 Makefile 与 workflow 注释里写明原因。
教训进踩坑 35。
