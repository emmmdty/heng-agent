# 十三期实施计划与决策

仍由 Agent 自主规划执行；本文件是决策记录。

范围：**让那 80-120 分钟的整轮评测不至于白烧**。

十一、十二期把用例集推到 40 条、把工具侧的缺口补齐了，但两期的成果都还等着
一轮真实评测验收。而现在这一轮有个明摆着的风险：

- `eval_regression.py` 的结果**只在整轮跑完后才落盘**。第 39 条崩了、
  网络抖一下、Ctrl-C 一次，前面 38 条真金白银烧掉的结果全部丢失；
- 前置条件（隧道、`code.stale`、语义缓存、故障注入是否启用）只有在开跑那一刻才被检查，
  而其中几项**在跑之前 5 秒就能验完**——白等 90 分钟才发现服务跑着旧代码是最贵的一种失败。

这一期不加任何新能力，只降这两个风险。仍然零 LLM 成本。

基线：`544 passed`，用例 40 条，`make check` 全绿（十二期 `468ca90`）。

## 一、决策

### 决策 1：增量落盘，而不是"跑完再写"

每条用例跑完即把当前全部结果写进 `eval/partial-<stamp>.json`（覆盖式全量写，
不是 append——JSON 数组 append 要么写坏格式，要么得自己维护括号）。
整轮正常结束、正式报告写完之后再删掉 partial。

为什么不做成"只在异常时保存"：**中断的形态里最常见的是 Ctrl-C 和进程被杀**，
那两种情况下没有机会执行保存逻辑。唯一可靠的做法是每条跑完就写。

代价是 40 次小文件写（每次几百 KB），相对一条用例 2-3 分钟的模型调用可以忽略。

### 决策 2：`--resume <partial.json>` 续跑，且**自动补回前置用例**

续跑跳过已完成的用例。但用例之间不是完全独立的：`memory-recall` 依赖
`memory-write` 先把偏好写进去（现有代码里靠"顺序执行"这条注释保证）。
跳过 `memory-write` 直接跑 `memory-recall`，评的是一个不成立的前提。

所以给用例加一个可选的 `requires` 字段，续跑时：
**待跑用例声明的前置若在已完成列表里，把它也一并重跑**。

不做成"全靠人记得"，理由与十期那条一样：**纪律写在文档里迟早会被绕开，
能编码进判据的就别只写文档**。`audit_cases.py` 顺带静态校验
`requires` 指向的用例真实存在——拼错一个 id 的代价否则要等到续跑时才暴露。

### 决策 3：`--dry-run` 把"能不能跑"的判断提前到 5 秒内

跑全部前置检查（`/health`、代码新鲜度、语义缓存、故障注入支持、用例选择、
事实表构建），打印本轮将跑哪些用例、哪些带故障注入，然后退出。**一次模型调用都不发。**

这不是新判据，是把已有判据的**发生时刻**提前。当前这些检查确实都在开跑前跑，
但人要先起服务、敲完整条命令、等它开始，才知道"哦，服务跑着旧代码"。
`--dry-run` 让这件事变成起服务之后的第一个动作。

### 决策 4：不做的事

- **不做失败用例自动重试**：一条用例失败可能是模型抖动，也可能是真缺陷。
  自动重试会把前者洗掉、把后者的复现率也一起洗掉，而这两件事恰恰要分开看
  （Bad-case 飞轮的分诊前提）。
- **不做并发跑用例**：用例之间共享同一个被测服务与网关配额，并发只会撞限流；
  且 `memory-write → memory-recall` 这类顺序依赖会直接坏掉。
- **不把 partial 做成断点续传的通用框架**：只服务这一个脚本，够用就行。

## 三、执行中的偏离

### 偏离 1：加了 `EVAL_BASE_URL`

`BASE_URL` 原先硬编码 `127.0.0.1:8000`。做 `--dry-run` 的真实验证时才发现：
要在**不打扰已有服务**的前提下体检另一个实例，根本指不过去。
改成 `os.environ.get("EVAL_BASE_URL", ...)` 一行，并削掉尾斜杠
（拼出 `//health` 时 FastAPI 会 404，而报错看起来像"服务没起来"，排查方向立刻跑偏）。
