## 一、这一轮读数指出了什么

### 发现 1：`compare-two` 的 P0 把正确答案判成了错的

判词：

    Agent 回复的 AeroHush Lite 单件到手价为 $51.26，按汇率 7.1 折算回 CNY
    为 363.946 元，与要求的 364 元不一致（差约 0.05 元）

Agent 是对的：query 说"寄到美国"，工具按美元口径返回 $51.26，
而 P0 写死的是 CNY 的 364。judge 反折回来撞上四舍五入，判了 FAIL。

**这是判据缺陷，不是 Agent 缺陷。** 而"判据把正确答案判成错的"比漏判更坏：
它会把人引去修一个不存在的问题，还会让真正的回归淹没在噪声里。

### 发现 2：`quote_basket_tool` 缺"分开买 vs 合并买"对照

金额出处扫描在 `compare-two` 里报了两处无出处：`$72.95` 与 `$3.65`。
查轨迹后确认 Agent **完全正确**——$69.30 是合单总价，
$72.95 是它明确标注的"分开买"对照（各付一次运费），$3.65 是省下的差额。

但这两个数**确实没有工具出处**：十一期只给 `optimize_basket_tool` 补了
`separate_purchase_landed_major` / `combining_saving_major`，
而对比类问题走的是 `quote_basket_tool`，它没有这两个字段，模型只能自己减。

**判据指的地方就是工具该补的地方**——这与八期补 `de_minimis_threshold`、
十一期补 `taxable_base` 是同一条。

### 不做的两条（同一轮扫出来，但属合理用法）

| 数字 | 场景 | 判断 |
|---|---|---|
| `$18.30 = 9.15 × 2` | 解释"分开买要付两次运费"的机制 | 解释性算术，不为它造工具 |
| `到手不到 $200` | 修辞取整 | 交接文档早写明：不要为一句修辞造工具，那是让判据牵着鼻子走 |

## 二、决策

### 决策 1：把对照字段下沉到 `quote_basket()`，优化器复用它

不是在 `quote_basket_tool` 里再算一遍。理由：优化器现在自己算了一份，
工具再算一份就是**三处口径**，而"分开买怎么算"这件事只该有一个定义。
下沉到领域层的 `quote_basket()` 之后，两个工具都从同一个 `BasketQuote` 上读。

顺带消掉优化器里的那段重复代码。

### 决策 2：`compare-two` 的 P0 同时写死两个币种口径

不是放宽判据。放宽（比如改成"与工具返回一致"）会让它失去检验能力——
这条用例本来就是为"组合运费不得重复计"写的定向探测。
改法是**把可接受的读数写全**：CNY 364 与 USD 51.26 都写进去，
并说明按 1 USD = 7.1 CNY 折算、四舍五入差异不算错。

判据要写 judge 判得了的事（十期的教训）：judge 手上有汇率表，
但它不知道"这两个数是同一个答案的两种写法"——那得由判据告诉它。

### 决策 3：smoke 档饱和这件事只记录，不在本期动

均分 0.967、11/12 PASS，比预期的 0.75~0.9 高。按十期的经验这说明区分度不足，
但**smoke 档的定位本来就是"日常快速回归"**，它的用例是十三期之前挑的老用例。
真正有区分度的新用例（故障注入、多轮链路、写路径）都在 full 档里。
所以结论是"该跑一轮 full"，而不是"该把 smoke 改难"。记进交接文档。
