# 十七期实施计划与决策

仍由 Agent 自主规划执行；本文件是决策记录。

范围：**给进程内的会话缓存加上限**——目前它们只增不减。

基线：`651 passed`，用例 44 条（`make check` 全绿），full 轮跑测进行中。

## 一、缺口

排查"按会话累积的判定器有没有人清理"时发现的一串：

| 进程内按会话累积的东西 | 每会话规模 | 清理时机 |
|---|---|---|
| `SessionRegistry._agents` | **一个 Agent + 整段 AgentState 上下文** | **无** |
| `SessionSources`（金额出处） | 最多 4000 × 2 个 float | **无** |
| `SequencingTracker`（顺序断言） | 一个工具名列表 | **无** |
| `OrderProvenanceTracker`（下单出处） | 商品/SKU 集合 + 订单指纹 | **无** |
| `LoopDetector` / `DriftDetector` | 小 | 每轮 reset ✓ |

前四个都提供了 `reset(session_id)`，但**没有任何地方调用它**。
后果：内存随"进程见过多少个不同会话"单调增长，直到重启。
本地开发看不出来（会话就那么几个），压测也看不出来（`loadtest.py` 用的会话数很少），
只有长跑的线上进程会慢慢涨——**而这类涨法没有任何一条告警会响**。

`SessionRegistry` 那一项尤其重：Agent 揣着整段对话上下文，
一个长会话可能是几十 KB 到几百 KB。

## 二、决策

### 决策 1：以 `SessionRegistry` 为准做 LRU 淘汰，其余判定器跟着它清

不让四个组件各自设上限。各自设上限会出现"Agent 还在、它的出处记录已经被挤掉"
的错配——那时出处校验会降级成警告（安全），但**判据静默变松了，没人知道**。

以会话生命周期为准只有一处判断，语义也清楚：这个会话被挤出内存了，
它的一切进程内状态一起清。

### 决策 2：淘汰是安全的，因为 `AgentState` 每轮都落盘

`orchestrator` 每轮结束调 `sessions.persist()`，被淘汰的会话下次再来时
`_try_restore()` 会把上下文读回来。所以淘汰**不丢对话**，只丢进程内缓存。

判定器的状态确实会丢（它们不落盘），后果是：
出处校验在那个会话上退回"无观测记录 → 警告"这一档（十四期就是这么设计的，
理由是快照恢复场景），顺序断言同理。**这是已经设计过的降级路径，不是新风险。**

### 决策 3：上限默认 200，可配

200 个活跃会话对单进程来说已经不小（每轮都要跑 LLM，真实并发远到不了）。
配成环境变量 `SESSION_CACHE_MAX`，0 表示不限（保留旧行为，便于排查时对照）。

### 决策 4：淘汰要留日志，但不发事件

日志一行足够（`已淘汰会话 X（当前缓存 N）`）。不发事件是因为
事件流是给买家侧前端看的，而淘汰是纯运维信息，塞进去只会污染时间线。
