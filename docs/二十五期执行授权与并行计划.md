## 一、批准了什么（逐项，含金额边界）

### 1. 预算方案四（两阶段，交接文档「五之一」P1-4 表的推荐项）

| 阶段 | 规模 | 用例执行 | 意图 | judge 调用（含位置互换） | 墙钟估 |
|---|---|---|---|---|---|
| 先导 | 主线 smoke 12 条 × k=2，两臂 diagonal | 48 | 48 | 48 | ≈ 0.7h |
| 全量 | 主线 44 条 × k=2，两臂 diagonal | 176 | 260 | 176 | ≈ 3.7h |
| 阳性对照 | 20 条行为相关用例 × k=2 × **cross 配对**（摘确认规则关键句的已知更差提示词） | 80 | 104 | 160 | ≈ 1.5h |
| 双 judge 一致率 | ≤20 对 × 2 顺序，`deepseek-v4-flash` 仅作第二 judge | — | — | 40 | ≈ 0.3h |
| **总账（最坏全跑）** | | **304** | **412** | **424**（longcat 384 + deepseek 40） | **≈ 6-7h，可过夜分摊** |

- 先导档 **不可下结论**（24 对 < 30 门槛），它的产出只有两个数：**实测平局率** 与 **位置互换自一致率**。
  全量是否改用 cross 配对（对数翻倍、被测成本不变）由先导的平局率决定：decisive 预估 = 88 对 × (1 − 平局率) ≥ 30 则维持 diagonal；不够先上 cross，再不够才考虑扩用例——**不许直接加样本量刷显著**。
- decisive < 30 时**如实写"样本不足，未达显著"**，这不是失败，是口径（"未达显著" ≠ "没有差异"）。
- 双 judge 一致率只作 judge 可信度证据，**不参与胜负判定，不与历史 rubric 分数横向比较**。
- 阳性对照臂是**有效性自证**：已知更差的提示词必须判出**负向显著**；判不出 = 工具有区分度缺陷，先修工具再谈胜负。

### 2. 候选提示词（臂 B）的立项与撰写授权

下一窗口自行设计并落地候选提示词，框架如下：

1. **假设必须来自观测**：R8（`eval/report-20260905-142017.json`）里三条 0.825-0.85 的 PASS
   （`clarify-missing-address` 漏复述数量 / `mixed-currency-basket` / `skip-confirm-refused`）
   与四轮无出处金额率波动（2.9%→4.3%→2.9%→4.0%，全部是解释性算术）是现成的假设来源。
   推荐：最小 diff 收紧确认卡/复述相关提示词段（要求下单前复述商品+数量+金额），
   可在 `order-confirm-card` / `skip-confirm-refused` / `order-full-cycle` 上可测量。
2. **只改 `app/application/prompts/heng.yml`**（候选臂通过内容差异体现），不改判据：
   `eval/cases.yaml` 的 rubric **一个字都不许动**——判据变了两臂读数不可比，且会污染 rejudge 指纹闸。
3. 改完提示词指纹必然变化：臂 A 基线仍跑 `a0915fac`（R8 已固化），臂 B 跑新指纹——
   **两臂指纹不同正是 A/B 的本意**，配置行 + `prompt_variant` 字段负责归因。
4. 候选提示词要过 `uv run python scripts/eval/audit_cases.py`（用例集自检不受提示词影响，跑一遍确认无连坐破坏）。

### 3. A/A 校验授权（管线shake-down，零风险）

真实 A/B 之前可先用 **A/A**（两臂同稿、仅 `prompt_variant` 标签不同）跑 2-4 条（`--only`）：
验证比较器→统计→报告整条链在真实 judge 输出上工作、拿到位置互换一致率的首个实测。
注意 A/A 的平局率是**结构性偏高**的（同稿内容），只能做管线验证，不能当平局率先验。

### 4. subagent 并行开发与验收授权

- **开发并行**：三线文件面不相交（冲突矩阵见交接文档「五之一」），A/B/C 三线可各自独立推进；
  线内也可拆 subagent（如 A 线：`ab_run` 真实路径 TDD 一个、候选提示词起草一个、报告渲染器一个）。
- **独立验收**：实现用的 subagent 与验收用的 subagent 分开派——验收方只拿 DoD/验收判据与产物，
  不看实现过程，独立跑验收命令给出 pass/fail 与证据。
- **交叉验收**：一个 subagent 的产出由另一个 subagent 从相反方向复核
  （如实现方跑测试证明能跑通，复核方专找静默塌缩与接线缺口——本仓两大火区）。
- **提交节奏**：按里程碑提交（本窗口的 3-commit 分主题模式可复用：fix / feat / docs），
  提交前 `uv run pytest -q` 全绿是硬前置；push 仍需用户单独说（本授权不含 push）。
- **每轮双验收不豁免**：subagent code review（审接线缺口与静默塌缩）+ 指标快照对比基线，
  两道都过才算里程碑完成。
