仍由 Agent 自主规划执行；本文件是决策记录。

范围：**写操作的出处校验**（交接文档第五节主线三③「写操作安全深化」）。

选它的理由：现在能做的都是无 key 任务（两条隧道 502、被测服务跑着旧代码），
而这一条是剩下的候选里**后果最重、判据最确定**的一个——订单是唯一会真的扣库存、
真的产生对外承诺的路径。

基线：`559 passed`，用例 40 条，`make check` 全绿（HEAD `792edb9`）。

## 一、现状与缺口

下单路径现有四道防护，逐条看它们**挡不住什么**：

| 现有防护 | 挡得住 | 挡不住 |
|---|---|---|
| `PlaceOrderUseCase` 的仓储查找 | 编造的 product_id / sku_id | 真实存在、但买家从没看到过的 SKU |
| Sequencing 断言（下单需先检索） | 完全没检索就下单 | 检索了 A，下单下成 B |
| 幂等键（会话 + 原话） | 同一句话重复提交 | 换个说法再下一单 |
| 权限白名单 + 确认卡语义 | 工具层越权 | 确认卡内容与实际下单参数不一致（确认卡只是提示词里的约定，没有任何代码校验它） |

**缺口一句话**：`create_order` 的商品参数**没有出处要求**。
模型可以下一个本会话工具从没返回过的 SKU——它可能来自自己的记忆、
来自同品牌的另一个变体、或来自买家早先提过但已经被否掉的候选。
仓储查得到，所以四道防护一道都不响。

这正是金额出处校验在写路径上的同一条缝：
**回复里的每个金额都要有工具出处**（八期做了），
**下单的每个 SKU 也要有工具出处**（本期）。
而且写路径的后果比回复严重——回复错了买家能看出来，订单错了库存已经扣了。

同品牌变体互串在本仓是**已知的**失败形态：`audit_cases.py` 整个脚本就是为它写的，
`conflict-budget-spec` 用例抓的也是"悄悄把 Lite 当降噪推给你"。
把它挡在写路径之外，代价只有几十行。

## 二、决策

### 决策 1：出处集合从**工具返回**里抽，不从回复里抽

抽取对象是 `tool.result` 的文本（中间件本来就拿得到），
用正则捞 `product_id` / `sku_id` 形态的标识符。
不去解析回复：回复是自然语言，模型完全可能提到一个 SKU 而不推荐它。

### 决策 2：硬拒，但沿用「有证据才硬拒」

与既有 Sequencing 断言同一条纪律：会话可能从 `AgentState` 快照恢复
（进程重启后内存里的观测记录为空），此时硬拒会误杀合法下单。
所以：**本会话观测到过工具返回、而下单的 SKU 不在其中 → 硬拒；
完全没有观测记录 → 降级为警告**。

为什么下单这条值得硬拒（而不是像其他断言那样只提示）：
库存扣减不可逆，"让模型下一轮自愈"这个前提在这里不成立——
错误的订单在模型自愈之前就已经落库了。

### 决策 3：重复下单只**提醒**，不拒绝

同会话内已为完全相同的 SKU 组合创建过订单时，注入一条警示，
带上已有订单号，让模型先跟买家确认是不是重复下单。

**不硬拒**：买家再买一份同样的东西是完全合法的行为，
拒掉它属于替买家做决定。而幂等键管的是"同一句话被提交两次"（传输层重复），
与"买家真的想再买一单"是两回事，不能用同一把锤子。

### 决策 4：不校验数量与地址

`quantity` 来自买家原话，工具返回里没有它的出处，硬要校验只能靠 NLP 猜测——
猜错的代价是拒掉合法订单。地址同理。
**只校验有确定出处的那一部分**，这与金额出处校验"范围刻意收窄、宁可漏报不误报"
是同一条纪律。

### 决策 5：放进独立模块 `order_provenance.py`

不塞进 `assertions.py`：那个文件现在 143 行、职责是"三类单步断言"，
出处校验是另一件事（它要记的是**返回内容**，而不是**调用顺序**）。
两者都由中间件调用，各自可独立测试。

## 四、执行中的偏离

### 偏离 1（本期最重要的事）：动手接线时发现 Harness 从没挂到业务工具上

原计划只是"把出处校验接进中间件"。接的时候顺着 `_resilience()` 摸下去才发现：
`HarnessToolMiddleware` 全仓**只在 `main_agent.py` 实例化一次**，
而那条链只挂给了主 Agent 自己的三个工具（task_dispatch / remember / forget）。
检索、计价、订单工具走的是各自工厂的 `_resilience()`——里面只有熔断中间件。

所以下面这些"已实现"的东西，在真正需要它们的工具上**一次都没跑过**：

- `create_order_tool` 的顺序硬拒（下单需先检索）
- `TOOL_REQUIRED_FIELDS` 的 schema 断言（含十一期专门给 quote/optimize 补的两条）
- L3 注入过滤 `sanitize_tool_output`——而检索与知识库返回恰恰是注入唯一可能进来的地方
- LoopDetector 只数得到派发与记忆工具

范围因此扩大：中间件链收成 `build_tool_middlewares()` 一份定义、三个工厂共用、
判定器由组装根注入，并加一条接线判据（`tests/test_harness_wiring.py`）。

**这不是顺手修的小事**：交接文档里"Sequencing 硬拒未误杀合法下单"那条端到端记录，
与"中间件压根没跑"是**同一种外观**。教训进踩坑 37。

### 偏离 2：补了一组"打开硬拒之后正常下单还下得成"的链路判据

接上护栏等于**打开一条从没在生产里跑过的硬拒路径**。判定器的单测证明不了
"接上之后真实订单还下不下得成"，而这条路径判错的代价是拒掉真实订单。
所以 `tests/test_order_write_path.py` 走真实工厂→工具→中间件→用例→仓储五条：
正常下单放行（最重要）/ 没检索就下单被拒 / 检索了 A 下单下成 B 被拒 /
重复下单带上已有订单号 / 组合优化的返回也算出处。

### 偏离 3：顺带给 L3 补了一条误伤判据

L3 现在第一次作用在商品卡上，命中会把片段替换成"[内容已过滤：疑似注入]"——
作用在商品文案上就是静默改坏给买家看的内容。拿全库 60 个 SPU 的真实检索返回
跑了一遍，零误伤，并把它钉成回归判据。
