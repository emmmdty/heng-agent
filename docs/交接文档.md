### 开工前必读的四条读数纪律

1. **读到 FAIL 先分诊，别直接去改 Agent。** 顺序是：判据写错了吗 → 环境挂了吗
   → 我自己操作错了吗 → 才是 Agent 的问题。
   二十期整轮 5 条非 PASS 的实际构成：**判据缺陷 2 / 环境故障 1 / Agent 真缺陷 2**。
   （十七、十八期那两轮是 5 : 3 : 1，判据缺陷占绝对多数；比例会变，**顺序不变**。）

2. **单条用例分数变化小于 0.35 不构成结论**，整轮 12 条均分的自然波动是 0.042
   （实测，`make variance`）。但**方差只解释分数波动，不赦免 P0 事实错误**——
   "编造了一个收货地址"是"发生了没有"，不是"高了低了"。

3. **一次 PASS 不是证据。** 二十期我拿一次定向重跑的 PASS 1.0 断定
   `conflict-budget-spec` 修好了，结果同一条在七轮历史里是
   `PASS PASS PASS FAIL FAIL PASS FAIL`——间歇性缺陷，一次绿灯什么都不说明。
   判"修好了"至少要连跑三次，且每次都读判词确认**待测行为真的发生过**。

4. **一条护栏"没误杀"不构成信息量，除非它真拦过一次。**
   二十一期新加的收货字段判据，定向重跑三轮全 PASS——但那三轮 Agent 根本没编造，
   护栏一次都没被检验到。真正的证据是它在 111 份历史流水上**红过一次**
   （抓到那条编造的地址，零误报）。**用例 PASS 不是护栏的验收证据**（踩坑 42）。

5. **在降级态量出来的结论，不能推广到正常态。** 同一次，我用 BM25 分
   3.035 < 门限 4.0 证明了"半入耳款不会被召回"——那是 `bm25_only` 档的读数；
   隧道恢复后走 `hybrid_rerank`，向量路照样把它召回来，缺陷原样复发。
   **改字面索引不影响 embedding。**

## 一、必须先知道的三件事

### 1. 只允许用三个模型（2026-09-04 更新，用户明确限定）

| 模型 | 角色 | 备注 |
|---|---|---|
| `mimo-v2.5` | 被测主模型 | **推理模型**，一个 trivial prompt 烧 ~190 completion token |
| `longcat-2.0` | 评测 judge + 回退模型 | 十三期前 judge 用的是 `deepseek-v4-flash`，**已不在允许清单内**，全部命令与默认值已改 |
| `Muse Spark 1.3` | 备选 | **需要挂代理**；代理不可用时就只用上面两个，不要找替代 |

**不要用其他任何模型**，即使 `/v1/models` 列出 34 个。
judge 必须与被测模型不同（同模型自评有自我偏好偏差），所以 judge 固定用 `longcat-2.0`。

> **2026-09-05 用户更新（二十五期任务配套）**：`deepseek-v4-flash` 可在**小样本双 judge 一致率**
> 场景作为第二 judge 使用（样本量不大时；仅作 judge 可信度证据，不作被测模型、不作整轮评测 judge）。
> 「judge 换模型分数不可比」的警告不变——双 judge 读数不与任何历史 rubric 分数横向比较。

代码里的默认值也已对齐（`settings.py` 的 `LLM_MODEL` / `LLM_FALLBACK_MODEL`、
`eval_regression.py` 的 judge 兜底、`Makefile` 的 `EVAL_JUDGE_MODEL`、
`.env.example`、`docker-compose.yaml`）——默认值指向不可用的模型，
出问题时的表现是"某台机器上跑不通"，而没有任何东西会告诉你原因是默认值。

**judge 换模型意味着分数不可比**：`longcat-2.0` 与 `deepseek-v4-flash` 的判别力不是同一把尺子，
十三期之前的所有分数都不能与新读数横向比较（同十期换 ground_truth 那次）。

网关会间歇性返 503（不只是限流）。八期整轮里实测到一次：mimo-v2.5 连续 503，
两次退避重试用尽后回退到 longcat-2.0，整轮没有报废——这是回退链**在真实故障下**
的第一次证据（此前只有单测）。

### 2. 每一次真实评测都在烧钱——**小样本先出读数，再放大**

40 条 Rubric 端到端评测 ≈ 80-120 分钟 + 大量 token。**开跑顺序是有规定的**
（2026-09-04 用户明确要求）：

1. **先把不需要 API key 的任务做完**——确定性判据、单测、静态自检、文档，
   这些不烧一分钱，也不占配额窗口。
2. **要用 key 时先跑小样本**：`--only <case_id>` 挑 1-2 条有代表性的，
   **拿到端到端结果并与预期指标对照**。注意判据是"读数符不符合预期"，
   **不是"跑通了没报错"**——smoke 跑通只证明链路活着，证明不了判据在起作用。
   十期的教训就在这：13/13 PASS、均分 1.000 的那一轮，三档全部顶格，
   改好改坏都看不出来。
3. **小样本读数符合预期之后**，才放大到 `--tag smoke`（12 条），再到全量 40 条。

每一档之前还要确认：
- `--dry-run` 前置全过（十三期加的，5 秒，一次模型调用都不发）
- `/health` 里 `semantic_cache: false`（脚本会自己拦，见地雷 6）、`code.stale: false`

### 3. 改完 `app/` 下的代码，必须重启 uvicorn

评测走 HTTP 打 8000 上的服务进程，而 Python 模块早在启动时就加载进内存了。
不重启的话，你评的是修复**之前**的行为——单测照样全绿（它读磁盘），
`/health` 的模型、提示词指纹、精排开关也一字不差。九期为此白跑了一轮定向回归。

十期起这件事有判据了：`/health` 报 `code.stale`，`eval_regression.py`
开跑前直接拦，并列出具体是哪几个文件、给出重启命令。看到这个拦截就重启：

```bash
ps -eo pid,args --no-headers | grep -F "uvicorn app.presentation.server" \
  | grep -v "grep\|zsh -c" | awk '{print $1}' | while read p; do kill $p; done
setsid uv run uvicorn app.presentation.server:app --port 8000 > uvicorn.log 2>&1 < /dev/null & disown
```

（`--allow-stale-service` 是逃生阀，只在你确实想评旧行为时用。
改 `scripts/`、`eval/`、`tests/` 不需要重启——它们不在服务进程里。）

### 先读这一段：五期的"隧道 502"其实是本地没接通（二十期实测）

十五到十九期，五份交接文档都把 `bm25_only` 降级态归因为"两条隧道 502"，
并把"恢复 GPU 服务"列为第一优先。**服务器端从来没挂过**：
`qwen_rerank_server` 从 09-03 13:45、`qwen_embed_server` 从 09-03 15:13
一直跑到 09-04，整个评测期间都在。缺的只是本地两条 `ssh -N -L`。

误判来自本机代理。`~/.zshrc` 里全局设了 `http_proxy=127.0.0.1:7890`，
而 `no_proxy` 写的是 `127.*` 这种通配——**curl 与 httpx 都不认**，
于是打 127.0.0.1 的探活被送进代理，代理连不上后端就回 **502 Bad Gateway**，
看着完全像远端服务坏了。

```bash
curl -m5 http://127.0.0.1:11437/health                     # 502  ← 像远端坏了
curl -m5 --noproxy 127.0.0.1 http://127.0.0.1:11437/health # 000  ← 真相：没人监听
```

代价：一条两行命令的修复被当成跨五期的外部阻塞，期间所有语义类读数都带着
降级折扣（105 条标注实测：语义类 Recall 0.940 → 0.350）。
**探活失败先分"连不上"还是"连上了但对面报错"，再下结论。**

#### 2. 新用例首跑挖出的真缺陷：目的国语义被工具搞错了

`de-minimis-boundary-eu` 首跑 **FAIL 0.325**。读判词发现不是判据苛刻，是真错：

买家问"寄到欧盟"，Agent 合理地把它翻成具体国家码，试了 `DE` 又试 `FR`
（工具参数当时写的就是"收货国家二位码，如 CN、US"，正是这么诱导的）。
规则表只认 `CN/US/EU/JP/SG`，于是：

- `product_search_tool`：**每一个商品**被逐个标成 `ship_to_unavailable`，
  Agent 看到的是"所有 TrailOx 都不发欧盟"——**一句事实错误，而它没有任何办法识破**。
- `quote_basket_tool`：报的是"P1002（TrailOx 20寸登机行李箱）不可寄往 DE"，
  同样把锅甩给商品。规则表里那句本来就带支持列表的错误，被商品可达性检查挡在了后面。

结果 Agent 放弃到手价，转而凭自己的知识说"欧盟免税额度约 €150"——
**正是八期补 `de_minimis_threshold_major` 要防的行为，从另一条路径又回来了。**

修法（两处都是"工具返回值要能自证边界"，同 `combine_hint`）：

| 位置 | 改动 |
|---|---|
| `catalog_search.execute` | 规则表不认识的目的国 → 当作没传（照常返回商品、不内联到手价），顶层给 `ship_to_unsupported{given, supported, note}`。**不再据此过滤商品**：系统没有德国的计价规则，不代表箱子不发德国 |
| `quote_basket_tool` | 规则表支持性校验**提到**商品可达性之前，错误里带支持列表与重试指引 |

#### 工作方式（对三条线的每个新窗口生效，四条硬纪律）

1. **指标先行**：开工第一件事是核对并冻结本节指标（判定公式 + 基线读数 + 门槛）。
   指标改动视为口径变更，必须回写本节并注明原因，不许先写代码再找指标。
2. **TDD**：先写完备测试（含边界与反例）再写实现，红 → 绿 → 重构。确定性纯函数
   （统计、判据、解析器）全部零 LLM 成本先做完；烧 token 的部分放最后，遵守
   「`--only` 1-2 条 → `--tag smoke` → 全量」的小样本纪律。
3. **每轮双验收**：一轮（红 → 绿 → 重构）收尾必须过两道——**subagent code review**
   （本仓惯例，重点审接线缺口与静默塌缩类缺陷）+ **指标快照**（对比基线读数，写进轮次记录）。
   两道都过才算轮次完成；结论与读数回写本文档与贡献证明。
4. **并行纪律**：三线文件面不相交（见文末冲突矩阵），各自分支独立推进；
   共享文件（`run_identity` / `composition.py`）的改动在合并前与另一线对齐。

#### 任务 A（主线）：Prompt A/B 分流（#11）

**目标与范围**：给已有的提示词版本化（`prompt_fingerprint` + `run_identity`）补上分流对比闭环，
用统计上站得住的读数回答"候选提示词是否更好"。方法论对齐业界通行做法：
Chatbot Arena / AlpacaEval / MT-Bench / Arena-Hard 的 **LLM-as-judge 成对比较 + 胜率**。
分流的最小可用形态是**评测侧**：按会话/用例把流量分到 A/B 两版并记录 variant；
在线按比例分流在评测读数站住之前不做（配额约束 + YAGNI）。

**指标定义（验收唯一口径）**：

| 指标 | 定义 | 门槛 | 行业参照 |
|---|---|---|---|
| **成对胜率（主指标）** | 同一用例同一输入，A/B 两版各采 k=2 次，longcat-2.0 **盲判**成对比较（judge 不知道版本身份），报 win/tie/loss | 护栏全绿前提下，胜率显著 > 50% 才可判"候选更优" | Chatbot Arena / AlpacaEval / Arena-Hard |
| **judge 位置互换自一致率** | 同一对样本正反两个顺序各判一次，两次裁决一致的比例 | **≥ 90%**，不达标该轮 judge 读数作废重跑 | MT-Bench 位置偏差控制的标准做法 |
| **显著性** | 去平局后符号检验 p < 0.05，且按用例重采样的 bootstrap 95% CI 不含 0.5 | 双双满足才算"显著"；decisive pairs < 30 不得下结论 | 统计通行口径 |
| **双 judge 一致率（条件项，已授权）** | 小样本（≤20 对）longcat-2.0 vs `deepseek-v4-flash`（2026-09-05 用户许可）对同一批成对样本的裁决一致率 | 只作 judge 可信度证据，**不参与胜负判定**，不与历史 rubric 分数横向比较 | 二十三期 rejudge 的跨模型版 |
| **护栏（一票否决，与胜率无关）** | ① `make check` 八项全绿；② full 44 条结算 PASS 率不低于基线（44/44）；③ 无出处金额率 ≤ 8%（同轮比较）；④ judge 均分 ≥ 基线 − 0.038（full 整轮散布）；⑤ completion P50 与轮延迟 P50 劣化 ≤ 10%（`make cost`） | 任何一条不满足即判"不可上线"，胜率再高也不行 | — |

**样本量与预算（2026-09-05 已授权，先小样本后放大）**：A/B 两臂 × 44 用例 × k=2 ≈ 2 整轮 full
的量（约 220 次意图）+ 阳性对照若干。用例间不独立是历史搁置理由，靠三点对冲：每用例 k 次采样
增加决定性配对、bad_cases 池与红队 11 条进样本池、仍不足时用 redteam 管线扩用例
（过 `audit_cases.py` 自检 + P0 工具真算）。**decisive pairs ≥ 30 是最低门槛**；达不到就如实写
"样本不足，未达显著"，不许加样本量刷到显著为止。

## 六、地雷清单（会真的浪费你时间的）

### 1. `pkill -f <关键词>` 会杀掉自己的 shell

Bash 工具的命令串里含该关键词时，`pkill -f` 会匹配到执行命令的 zsh 包装进程，
表现为命令以退出码 144 中断、后续步骤全部没跑。

```bash
# 错
pkill -f eval_regression; <后续命令>            # 后续不会执行

# 对
ps -eo pid,args --no-headers | grep -F "eval_regression" \
  | grep -v "grep\|zsh -c" | awk '{print $1}' | while read p; do kill -9 $p; done
```

同理 `pgrep -f <关键词>` 会自匹配，导致"进程还在"的误报。

### 2. `nohup ... &` 在后台工具里同样会被 SIGHUP 带走

八期又踩了一次：用 `run_in_background` 起 `nohup ... &`，日志 0 字节、
退出码却是 0（那是包装进程的退出码），而**真正的进程还活着**，
第二次重跑时两个进程一起抢 Qdrant 文件锁。
必须 `setsid ... > log 2>&1 < /dev/null & disown`，并且重跑前先按地雷 1 清干净。

### 3. Qdrant 本地嵌入模式是单进程文件锁

`uvicorn` 在跑时不能同时跑召回评测脚本（`data/qdrant` 被占）。
顺序是：停服务 → `rm -rf data/qdrant` → 跑评测 → 起服务。

### 4. 输出被管道缓冲，看不到进度

`uv run python ... | tail -N` 会让 Python 的 stdout 变块缓冲，跑完才有输出。
**十期又踩了一次**：`make eval 2>&1 | tail -45` 跑整轮，全程看不到任何进度，
而且 28 条的输出远超 45 行、前面的全丢了（报告文件不受影响，所以损失只是盲跑）。
长任务要看进度就别接 `tail`；实在想看，用产物做进度信号：

```bash
find data/conversations -name "*.jsonl" -newermt "HH:MM:SS" | wc -l   # 已跑完几条
```

长任务用 `setsid ... > log 2>&1 &` + `until grep -q <完成标志> log; do sleep N; done`
（用 `run_in_background: true`），并且加 `python -u`。

### 5. `hasattr` 在 AgentScope 的 dict 子类上会漏 KeyError

`ChatResponse` 继承 `DictMixin` → `dict`，属性查找走键查找，缺键抛 `KeyError`，
而 `hasattr` / `getattr(obj, name, default)` 只吞 `AttributeError`。
碰到这个类型别用属性反射。

### 6. 工具模块不能写 `from __future__ import annotations`

AgentScope 用 pydantic 从函数签名动态生成 JSON schema，字符串化注解会解析失败。
新增工具时注意。`app/application/harness/` 下的判定模块**可以**写（不进 schema 生成）。

### 7. 自建 OpenAI 兼容服务必须返回 `usage`

`rag.KnowledgeBase` 直接取 `usage.total_tokens`。缺了它商品索引一切正常、
品类知识库静默建库失败——同一服务喂两个消费者只挂一个，症状离故障点很远。

### 8. 评测脚本读 `os.environ`，必须先导入 settings 才有 `.env`

已修（导入 `app.infrastructure.settings` 触发 `load_dotenv`）。新写脚本时注意同样的坑。

### 9. AgentScope 的 `Msg` 只收关键字参数，且 content 必须是 block 列表

`Msg("main", text, "assistant")` 会抛 pydantic 校验错误。正确写法：
`Msg(name="main", content=[TextBlock(type="text", text=...)], role="assistant")`。
**更要命的是**：编排器有兜底 `except Exception`，这个错误会被吞成
`final_text = "[error] ..."`，于是"断言某事没发生"的测试全部平凡通过。
写编排器测试时必须加哨兵断言（见 `tests/test_orchestrator_provenance.py`）。

### 10. 落盘顺序不等于发生顺序

`JsonFileConversationStore` 一轮结束后**先写两条 turn、再批量写 events**，
所以文件里工具返回永远排在回复之后。按行顺序"边读边判"会让出处集合恒为空，
指标恒为 100%——而这个错误的读数看上去和真实读数一样像模像样。
读流水做指标前，先整份读完再判（`scripts/eval/trace_audit.py` 已按此实现）。

### 11. `kill` 掉 `uv run` 只杀了外壳，uvicorn 还活着

`uv run uvicorn ...` 是一条进程链：`uv run` → `python .venv/bin/uvicorn`。
`kill` 掉前者，**后者继续监听端口**——`pgrep -af uvicorn` 看着像已经停了
（那几条 wrapper 没了），`curl /health` 却照样 200。
后果不是"没停干净"这么轻：下一次用同一个 `DATA_DIR` 起服务会撞上
Qdrant 本地模式的文件锁（地雷 3），而报错指向的是锁，不是那个没死的进程。
停服务时按端口确认，别按进程名：

```bash
pgrep -f "bin/uvicorn app.presentation"     # 看真正在跑的那个（带 .venv 全路径的）
kill <那个 PID>
curl -s -o /dev/null -w "%{http_code}" --noproxy 127.0.0.1 http://127.0.0.1:8000/health   # 000 才算停了
```

顺带一条同场景的：
要在**不打扰已有服务**的前提下起第二个实例，用 `VECTOR_STORE_DIR=<临时目录>`
换一份向量库存储——**不要改 `DATA_DIR`**（二十期改的，此前这里写的正是后者）。
`DATA_DIR` 决定流水落点，把它指到临时目录等于让这一轮的证据随目录一起消失：
报告留在仓库 `eval/` 里、指着一个不存在的路径，无出处金额率 / 算式自洽 /
bad case 采集事后一条都算不回来（2026-09-04 实测，十九期整批读数因此作废）。
现在 `eval_regression.py` 开跑前会直接拦下这种配置。

### 12. 本机代理会把"没人监听"伪装成远端 502（最贵的一条）

`~/.zshrc` 全局设了 `http_proxy=127.0.0.1:7890`，而 `no_proxy` 写的是 `127.*`——
**curl 与 httpx 都不认这种通配写法**。于是所有打 127.0.0.1 的请求都被送进代理，
后端没人监听时代理返回 **502 Bad Gateway**，看着完全像远端服务坏了。

```bash
curl -m5 http://127.0.0.1:11437/health                     # 502  ← 假象
curl -m5 --noproxy 127.0.0.1 http://127.0.0.1:11437/health # 000  ← 真相
```

**这条坑的代价是本仓最贵的一次**：十五到十九期整整五期，交接文档都把
`bm25_only` 降级态归因为"两条隧道 502"、把"恢复 GPU 服务"列为第一优先，
而服务器端从头到尾都是好的，缺的只是两条 `ssh -N -L`。
期间所有语义类读数都带着降级折扣（语义类 Recall 0.940 → 0.350）。

纪律：**打本地端口一律加 `--noproxy 127.0.0.1`**；
探活失败先分清"连不上"（连接层）与"连上了但对面报错"（应用层），再下结论。
这是经验 9「一个错的解释比没有解释更坏」在环境诊断上的同一条。

### 13. `BatchMode=yes` 遇上未知 host key 不问就失败（接手须知引用过它，条目一直没写）

二十一期开工实测：`ssh -o BatchMode=yes gpu-5090 hostname` 报
`Host key verification failed`，而远端两个服务已正常跑了 20+ 小时。
根因是 **known_hosts 里压根没有这台机器的条目**（cpolar 端口轮换后新地址
从没被记过），`BatchMode` 遇到未知 host key 不提示、直接失败——
外观与"服务器挂了"一模一样。

```bash
ssh-keygen -R '[29.tcp.cpolar.top]:10857'            # 旧条目清理（没有就忽略）
/home/tjk/.local/bin/cpolar-ssh-update               # 端口轮换后先更新配置
ssh -o StrictHostKeyChecking=accept-new gpu-5090 hostname   # 接受新 host key
```

代价 20 分钟。与地雷 12 同族：**探活失败的第一步永远是分层——
连不上 / 连上了但握手失败 / 握手了但对面报错**，三层的修法完全不同。

## 七、工作方法上的经验

**1. 评测跑的链路必须和线上跑的链路是同一条。**
七期自查发现 BM25 索引只在 `scripts/eval/*` 里构造、从没接进 `composition.py`——
评测选出的最优配置根本没上线，而且因为混合召回是"缺省 None 即退回原行为"的
加法式实现，"忘了接线"和"故意关掉"外观完全一样，没有任何告警。
新增可选依赖时，给它配一条启动期的显式声明**和一条钉住接线的测试**。

**2. 落盘的轨迹必须和喂给模型的返回是同一份。**
这是第 1 条的孪生问题，错在观测侧。八期首次扫描报出 13.4% 无出处金额，
逐条核对发现其中一半是假的——`tool.result` 事件是手挑字段拼的，
`filtered_out` / `insights` 后来加进返回值时没人记得同步事件。
**先怀疑观测，再怀疑被观测者。**

**3. 单次评测分不清"修好了"和"这回没触发"。**
加严 rubric 后重跑 `compare-two` 得 PASS，读判词才发现这次 Agent 根本没给组合总价，
新判据压根没被检验到。八期的修法是把用例改成**定向探测**——
query 明确索要组合总价，让待测行为每轮都发生。**能被跳过的判据等于没有判据。**
验收同理：memory-recall 修完连跑三次并逐条读判词，不是跑一次看绿。

**4. 交接文档自己也会过期，"顺手就能做"的那种最危险。**
八期结尾写"下轮顺手扫一次，成本为零（扫的是已经落盘的流水）"。
九期照做，拿回来一个一模一样的 6.7%——修复比流水晚两分钟，
已落盘的轨迹里压根没有那个新字段。写文档的人当时清楚修复刚落地，
但没意识到"已经落盘的流水"正是修复之前的产物。
**接手时遇到任何"零成本就能拿到新读数"的说法，先核对产物时间戳与代码 mtime**——
一次 `ls -l --time-style='+%m-%d %H:%M'` 比一次重扫便宜得多，
比一次白跑的整轮便宜几个数量级。

**5. 判据只能写 judge 判得了的事。**
judge 看到的是 transcript + ground_truth，**看不到工具调用与返回**。
十期给 `de-minimis-boundary-eu` 写了一条 P0「该数值必须来自工具返回」，
判词回来是"对话记录中未显示工具返回…按拿不准按不通过处理"——
Agent 那个 1170 明明是工具给的（轨迹里 `de_minimis_threshold_major: 1170.0` 白纸黑字），
**判据本身写错了位置**。正确的拆法是各归其位：
数值对不对 → 判据写死具体数字，judge 拿 ground_truth 核对；
有没有出处 → 交给金额出处校验，它扫轨迹，是确定性的。
顺带一条：judge 手上没有规则表时，它对到手价**只能验自洽、验不了正确**
（实测放过了"1,199 × 12% ≈ ¥3.48"这种基数写错、结果碰巧对的推导）。
十期把关税费率、免税额度、运费公式补进了 `build_ground_truth()`。

**6. "修了但读数没变"，第一嫌疑人是观测链路，第二才是代码。**
这是第 2 条在部署维度的同一条。九期照着交接文档去查"还有第三条没覆盖的代码路径"，
查了半天代码是对的——真相是被测服务比修复早启动 6 分钟，进程里跑的是旧代码。
**核对产物时间戳时，除了流水 mtime 与代码 mtime，还要核服务进程的启动时刻**
（`ps -eo pid,lstart`）。现在这条已经变成判据了（`/health` 的 `code.stale`
+ 开跑前拦截），但同型问题会换个地方再来：任何"跑起来之后就不再重读"的东西
——已加载的模块、缓存的配置、建好的索引——都有这个毛病。

**7. 写在文档里的纪律迟早会被绕开，能编码进判据的就别只写文档。**
"无出处金额率只在同一轮内横向比较"这句话八期就写在交接文档里了，
而门禁恰恰是拿绝对值比阈值的，扫的又是只增不减的累积目录——
纪律与判据当场打架，红灯来得毫无悬念。修法不是调阈值（那是让门禁慢性死亡），
是把比较口径编码进判据本身（`--report latest` 收敛到本轮）。
**下次写下"注意只能在 X 条件下比较"时，先问一句：这个条件能不能写进代码。**

**8. 一条新用例的价值，看它挖出了什么。**
15 条新用例里，`de-minimis-boundary-eu` 首跑 FAIL 0.325，读判词挖出的是
Agent 拿不到欧盟到手价、转而凭自身知识作答——而根因在工具侧
（目的国语义 + 参数描述诱导），不在 Agent。修完同一条用例 0.325 → 0.492，
P0 的到手价那条从 FAIL 转 PASS。
**扩用例集不是为了让分数好看，是为了让缺陷有地方冒出来。**
所以新用例首跑 FAIL 是预期结果，要做的是逐条读判词分清三件事：
Agent 真错了 / 判据写错了 / judge 判不了——这一条用例三样都占了。

**9. 一个错的解释比没有解释更坏。**
金额出处校验会给无出处金额推断成因（"疑似 A + B"）。容差按 1% 放宽时，
它会把 1619.9 认成 1625.9 的成因——看起来言之凿凿，实际把人引向错误的根因。
收紧到 ±1 绝对容差后，凑不出来的就老实标 `unsourced`。
诊断类输出宁可少说，不可说错。

## 八、最终呈现与求职定位（二十二期收尾时以"苛刻面试官"视角写下）

先说清楚这是什么项目：**求职作品，不是线上生产系统。**
没有真实流量、没有第二个人、没有运维。这不是缺陷，是处境——
但**呈现方式必须主动把它说出来，而不是等面试官戳破**。

### 八之一、最终呈现是什么样子（做完长这样）

一个求职项目的最终形态不是"更多功能"，是**一套可复现的证据链 + 一个能跑的演示 + 一组能讲深的工程故事**：

| 呈现物 | 现状 | 还差什么 |
|---|---|---|
| **README**（5 分钟读完：是什么 / 怎么做硬 / 数字 / 边界） | 已有，但偏"开发者自用" | 补一个"三分钟版"开头：三句话说清定位 + 四个数字 + 一句边界声明 |
| **贡献证明**（`docs/贡献证明.md`：每个数带复现命令） | 已有，二十二期建起 | 二十三期清单 1-3 跑完回填（双指标 / 成本延迟 / judge 一致性） |
| **设计演进叙事**（21 期决策 + 50 条踩坑） | 已有，是最独特的资产 | 不用加内容，用：挑出 3 个可讲 10 分钟的深故事（见八之三） |
| **演示**（能跑的东西） | 前端 + WebSocket + Docker Compose 都在 | 缺一个 **scripted demo**：一条固定会话脚本把"数字全有出处、确认卡、故障降级、偏好记忆"四件事串起来，10 分钟能复演；有精力再录屏 |
| **面试问答**（对最尖锐问题的准备） | 散落在各文档 | 八之二的问题清单 + 答法，过一遍即可 |

### 八之二、苛刻面试官的五个攻击点与答法（背下来，别临场编）

**Q1 "用例、标注、judge、判据全是你自己写的——自评闭环，分数不可信。"**
答：承认前半句，这是没有人工时的结构性限制。然后给三层替代证据：
① P0 数字全部由工具真算（不是手填）；② 8 条行为判据里 8 条已确定性化，
judge 只剩语义分——而 judge 自身一致性在量（二十三期清单 3）；
③ 分诊记录证明判据错了 5 次、judge 判不了 2 次——**我把自己评测体系的错误全部留档**，
这比"一次都没错过"更可信。

**Q2 "44 条用例、60 个商品、单人标注，规模撑不起任何结论。"**
答：对，所以结论从不写成"系统准确率 99%"，全部带规模声明。
这套项目的产出不是那个 0.992，是**判据工程方法**：每条判据可复现、有真红记录、有误报控制。
规模是处境，方法是可迁移的。

**Q3 "P50 8.6 秒，这也叫生产级？"**
答：不叫，文档里从头到尾写的是"研发级"。延迟是模型约束（用户限定推理模型）的后果，
工程上能做的是网关限流、语义缓存、削峰队列——这些都有。换非推理模型是配置项不是架构项。

**Q4 "无出处金额率这个指标，模型少写数字就能刷好，你堵了吗？"**
答：堵的方向是把暴露面拆成两个数分开报告（二十三期清单 1）；
根本做法是指标跟着根因修复走——13.4% → 2.9% 靠的是补工具字段，不是调阈值。

**Q5 "能力清单上的你都有，清单之外你有什么？"**
答：能力清单覆盖的是基线能力（Hook Pipeline、混合召回、记忆层——16 项对齐 DONE）。
本仓的增量是**把"可信"做成工程**：8 条从 judge 迁移来的确定性判据、八项 15 秒零成本门禁、
每道护栏"真红一次 + 零误报"的证据链、50 条踩坑档案。
一句话：能力清单回答怎么建 Agent，这个项目回答了"你怎么知道你的 Agent 没在骗你"。

### 八之三、三个能讲 10 分钟的深故事（面试叙事库，按深度排）

1. **"修在模型走不到的路上"**（二十一期→二十二期）：attribute_mismatch 先加在 hits 上，
   三轮全 PASS——但那条用例里商品必然被预算挡进 filtered_out，声明根本没到模型手上。
   修了两次召回都没用，最后动的是返回结构。教训：**接线缺口的外观与"修好了"完全一样**。
2. **"护栏必须真红过一次"**（十四期→二十一期）：Harness 中间件从没挂到业务工具上，
   端到端记录写着"硬拒未误杀"，实际一次都没跑过。验收标准从此改写：
   用例 PASS 不是护栏的证据，**一次真实的拒绝 + 零误报才是**。
3. **"一个错的解释比没有解释更坏"**（经验 9 / 地雷 12）：代理把"没人监听"伪装成 502，
   五期交接文档把隧道问题归因成服务器故障——期间所有语义类读数带着降级折扣。
   修法是分层探活 + 把"只在 X 条件下比较"的纪律编码进判据。

### 八之四、离"做完"还有多远（求职项目口径）

| 状态 | 内容 |
|---|---|
| **已经到** | 能力层（能力清单 16 项 DONE + 9 项基线外自加）、判据层（8 迁移 + 八项门禁）、证据层（贡献证明全表可复现）、R6 正常态基线（44 条结算全 PASS） |
| **二十三期清单一遍做完后到** | 证据链的自动化部分**到顶**：双指标、成本延迟、judge 一致性、方差 n≥3、红队用例、soak——此后**边际收益递减，不要再加** |
| **永远不做** | 假装生产级；为凑 kappa 找"半个标注人"糊弄；跑 50 轮 full 刷方差的小数点；给简历加任何本文档边界声明之外的数字 |
| **简历上的写法** | 每个量化句带一个边界从句。例："构建确定性判据体系（8 类行为从 LLM judge 迁移为可复现判据，提交门禁 15s 零模型成本）；端到端 44 条合成用例全 PASS——**自建评测，无真实流量，定位为可信度工程方法验证**" |

**给下一个会话的一句话**：这个项目最值钱的是"知道自己的数不能证明什么，并且写下来了"。
二十五期做 A/B 与两条并行线时，**指标验收就是本节纪律的延伸**：胜率不显著就如实写
"未达显著"，不许加样本量刷到显著为止；面试官不会数你的门禁有几项，但会看你是否清楚每一项的适用边界。
