## 一、必须先知道的三件事

### 1. 网关只有三个模型可用（配额限制）

`mimo-v2.5`（被测主模型，**推理模型**，一个 trivial prompt 烧 ~190 completion token）、
`deepseek-v4-flash`（评测 judge，`response_format: json_object` 支持良好）、
`longcat-2.0`（回退模型）。

**不要用其他模型**，即使 `/v1/models` 列出 34 个。judge 必须与被测模型不同族
（同模型自评有自我偏好偏差）。

网关会间歇性返 503（不只是限流）。八期整轮里实测到一次：mimo-v2.5 连续 503，
两次退避重试用尽后回退到 longcat-2.0，整轮没有报废——这是回退链**在真实故障下**
的第一次证据（此前只有单测）。

### 2. 每一次真实评测都在烧钱

13 条 Rubric 端到端评测 ≈ 25-40 分钟 + 大量 token。跑之前务必：
- 先用 `--only <case_id>` 单条验证链路通了
- 确认 `/health` 里 `semantic_cache: false`（脚本会自己拦，见地雷 6）
- 确认异常会当场打印（已修）

---

### 3. 改完 `app/` 下的代码，必须重启 uvicorn

评测走 HTTP 打 8000 上的服务进程，而 Python 模块早在启动时就加载进内存了。
不重启的话，你评的是修复**之前**的行为——单测照样全绿（它读磁盘），
`/health` 的模型、提示词指纹、精排开关也一字不差。九期为此白跑了一轮定向回归。

十期起这件事有判据了：`/health` 报 `code.stale`，`eval_regression.py`
开跑前直接拦，并列出具体是哪几个文件、给出重启命令。看到这个拦截就重启：

```bash
ps -eo pid,args --no-headers | grep -F "uvicorn app.presentation.server" \
  | grep -v "grep\|zsh -c" | awk '{print $1}' | while read p; do kill $p; done
setsid uv run uvicorn app.presentation.server:app --port 8000 > uvicorn.log 2>&1 < /dev/null & disown
```

（`--allow-stale-service` 是逃生阀，只在你确实想评旧行为时用。
改 `scripts/`、`eval/`、`tests/` 不需要重启——它们不在服务进程里。）

| 阶段 | 会话 | 金额总数 | 无出处 | 无出处率 |

**这个数不是错误率，是"回复里有多少钱是模型自己算的"**（暴露面）。
两轮间 4.9% → 6.7% 不是回退：**这个指标有明显的轮次间波动**，
因为它取决于模型这一轮愿意写多少解释性算术（第二轮它主动算了
"分开买合计 $72.95""合单省 $3.65"）。**只在同一轮内横向比较，
不要拿两轮的绝对值当趋势。**

两轮里判据抓到的**真问题**（都已修）：
1. 非主 SKU 到手价（$238.15）——模型自己算的，已由逐 SKU `landed_price` 覆盖
2. 跨币种折算（149 USD 写成"约 ¥1080"，正确 ¥1057.9）——已由 `price_in_target_major` 覆盖
3. 免税额度阈值（"美国 $800 以下免税"）——工具原先只回 `de_minimis_applied: true`
   从不回阈值，模型凭自己的知识说；改了规则表它照样说 800 且不会报错。
   已加 `de_minimis_threshold_major`。**这条是在第二轮读数之后修的，
   所以 6.7% 这个数里还含着它**，下一轮应当更低。

> **九期复扫仍是 6.7%（89 处金额 / 6 处无出处），一字未变，两处 `$800` 原样都在。**
> 这不是修复失效，是八期那句"重扫一次就能拿到新读数"本身不成立——
> 原因与正确做法见第五节「开工第一件事」。

剩下的都是合理用法（"分开买 $72.95""省 $3.65""到手不到 $200"——
对已有出处数字的对比或修辞取整）。

- 优化器 16 条单测全绿，**拿真实商品算 ground truth 时才发现它给出荒唐答案**

  自造样本会不自觉地造得"均匀"，真实数据里最容易出事的是极端比例。

#### 1. 用例集 13 → 28 条，补齐七个空白类别

`eval/cases.yaml` 新增 15 条，每条的 P0 数字都由 `TariffSchedule` **真实算过**
（不是手算），判据写死具体金额而不是"与工具一致"——judge 判不出来的算术错误
才抓得到。新增类别：歧义澄清（含**反向判据** `no-over-clarify`：不该问时多此一举
同样算失败）、冲突约束、免税额度临界、多币种混合篮子、多轮改主意、库存边界、越权边界。

配套：`--tag smoke|full` 分层（日常 10 条 / 全量 28 条）。
`full` 不需要逐条标注，所有用例隐含属于它——漏标 tag 不会让某条用例静默不被跑到。

#### 2. 新用例首跑挖出的真缺陷：目的国语义被工具搞错了

`de-minimis-boundary-eu` 首跑 **FAIL 0.325**。读判词发现不是判据苛刻，是真错：

买家问"寄到欧盟"，Agent 合理地把它翻成具体国家码，试了 `DE` 又试 `FR`
（工具参数当时写的就是"收货国家二位码，如 CN、US"，正是这么诱导的）。
规则表只认 `CN/US/EU/JP/SG`，于是：

- `product_search_tool`：**每一个商品**被逐个标成 `ship_to_unavailable`，
  Agent 看到的是"所有 TrailOx 都不发欧盟"——**一句事实错误，而它没有任何办法识破**。
- `quote_basket_tool`：报的是"P1002（TrailOx 20寸登机行李箱）不可寄往 DE"，
  同样把锅甩给商品。规则表里那句本来就带支持列表的错误，被商品可达性检查挡在了后面。

结果 Agent 放弃到手价，转而凭自己的知识说"欧盟免税额度约 €150"——
**正是八期补 `de_minimis_threshold_major` 要防的行为，从另一条路径又回来了。**

修法（两处都是"工具返回值要能自证边界"，同 `combine_hint`）：

| 位置 | 改动 |
|---|---|
| `catalog_search.execute` | 规则表不认识的目的国 → 当作没传（照常返回商品、不内联到手价），顶层给 `ship_to_unsupported{given, supported, note}`。**不再据此过滤商品**：系统没有德国的计价规则，不代表箱子不发德国 |
| `quote_basket_tool` | 规则表支持性校验**提到**商品可达性之前，错误里带支持列表与重试指引 |
| 两个工具的 docstring | "收货国家二位码"→ 显式枚举 `CN/US/EU/JP/SG`，并写明"EU 是整个欧盟，不要填 DE、FR" |
| `tests/test_tools_and_eventbus.py` | 钉住 docstring 枚举与规则表一致——schema 从 docstring 生成、没法动态取值，必然有脱钩的一天 |

#### 3. 服务跑着旧代码，而单测和 /health 都不会报警

九期交接留的尾巴（免税额度阈值重扫）本身没问题，但**重跑两条用例后读数一字未变**。
根因不在代码：`uvicorn` 16:43:06 启动，修复 16:49:20 落地，进程再没重启。
单测读磁盘所以全绿，`/health` 报的模型、提示词指纹、精排开关全都一字不差——
**没有任何一处观测能区分"新代码"和"跑着旧代码"**。

| 位置 | 改动 |
|---|---|
| `harness/run_identity.code_identity()` | 比对**源码 mtime vs 进程启动时刻**（比 git sha 可靠：踩坑当时正是未提交状态） |
| `/health` | 增报 `code{started_at, source_mtime, stale, stale_files}` |
| 报告开头那行 | 渲染"代码 新鲜(服务启动于 …)"或"⚠️已过期(…在那之后被改过)" |
| `eval_regression.py` | **开跑前拦截**，列出具体是哪几个文件、给出重启命令（`--allow-stale-service` 是逃生阀） |

修完重跑，`$800` 消失：同样两条用例的无出处金额率 **20.0% → 9.3%**，
`landed-price-us` 从 3 处降到 0 处。

#### 4. `make check` 门禁（零 LLM 成本，十几秒）

仓库此前既无 Makefile 也无 CI。现在 `make check` = 单测 + 标注集自检 +
用例自检 + 金额出处门禁；另有 `make eval` / `make eval-smoke` / `make health` / `make serve`。

#### 5. 金额出处门禁的扫描范围收敛

`data/conversations/` 是累积目录，旧流水不会消失。扫全量时修复前那两轮的
`$800` 仍在分子里，全量比率 10.2% > 阈值——**"只在同一轮内比较"这条纪律
写在文档里，判据却没有实现它**。现在报告记 `session_id`，
`--report latest` 把范围收敛到最近一轮；范围内一份流水都匹配不上时报错退出
（0 处金额算出的 0% 会被当成满分放行，比红灯更危险）。

#### 6. 用例自检支持"显式对比"

`audit_cases.py` 原判据要求每个品牌词收敛到唯一 SPU，而免税额度临界最干净的
对照恰恰是同系列两款箱子。现在 query 把每个候选都点名时判为对比而非歧义，
边界卡死在"全部"（只点名一部分时剩下那些仍算歧义）；
并新增一类检查：显式对比时 rubric 必须把被点名的变体**都**钉住，
只钉一个的话另一个答错也照样 PASS。

这正是 `_to_card` 里 `combine_hint` 那段注释在防的事；
新工具内部算的时候同样会踩，写测试钉住。

### 十期挖出的具体缺陷（1 / 2 十一期已修，3 已被工具覆盖）

**1. Agent 会写出错误的计税基数。**（工具侧十一期已补 `taxable_base_major`，但 Agent 的行为是否真的改了，要等新一轮 `make eval` 才有读数）
`de-minimis-boundary-eu` 实测：最终关税 3.48 元是对的（工具给的），
但解释写成"**1,199 × 12% ≈ ¥3.48**"——计税基数写成了整单金额
（1199 × 12% = 143.88，差了 40 倍）。数字对、过程错。
判据已经抓住它了（P0 那条"不得写成对整单计征"当前是 FAIL）。
**先别急着改提示词。** 工具已经回了 `de_minimis_threshold_major` 与 `tariff_rate`，
但没回"应税基数"（超出免税额度的那部分）。补一个 `taxable_base_major` 字段，
让模型有得可抄，比在提示词里讲道理更可能奏效——同 `combine_hint` 的思路。

金额出处校验已经实锤了这条缝：修完目的国之后那一轮，Agent 答对了，
但仍有两处无出处金额，都是 **`€3.72`**——正是它自己减出来的应税基数
（153.72 − 150）。**判据指的地方就是工具该补的地方。**

**2. 免税额度只有目标币种口径，原生口径没有出处。**（十一期已修：规则表改存原生口径）
规则表里 US 的额度本来就定义为 `800 * 710`（即 800 USD）、EU 是 `150 * 780`（150 EUR），
但存的是折算后的 CNY 分，`de_minimis_threshold_major` 也只按 `target_currency` 回一个值。
于是 `target_currency=CNY` 而买家语境是美国时，Agent 想说"美国免税门槛"就只能自己反折：
实测它写的是"美国免税门槛 **$800**（约 ¥5680）"——5680 有出处，800 没有。
这正是八期修 `de_minimis_threshold_major` 想堵的那个 `$800`，
换成"跨币种表述"这条路径又回来了（第三次了：八期堵了"凭知识说"，
十期堵了"工具没被调到"，这次是"调到了但口径不对"）。
修法：规则表里把原生口径（币种 + 金额）记下来，`to_dict()` 一并回传，
让 Agent 说 "$800" 时有得可抄。（十一期已按此修：常量改名 `_DE_MINIMIS_NATIVE`
存 (金额, 币种)，CNY 由汇率表推导；`tests/test_pricing.py` 原先钉的 `5680.0`
与 `800.0` 两个口径都保住了。）

**3. 三处缝**（判据一直在报）：

| 场景 | 状态 | 判据里的表现 |
|---|---|---|
| 预算差额（"预算还剩 $22"） | 十一期已补 `remaining_major` | 曾是 `suspected_difference` |
| 分开买 vs 合并买的差额（"省 $3.65"） | 十一期已补 `combining_saving_major` | 曾是 `suspected_difference` |
| "再加多少能配上" | 十一期已补 `additional_budget_needed_major` | —— |
| 修辞取整（"到手不到 $200"） | **不修** | `suspected_sum` / `unsourced` |

前三条由 `optimize_basket_tool` 覆盖，但**工具存在不等于模型会调**——
新基线跑出来时要看这几个数是不是真的带上了出处。
**第四条（修辞取整）不要为它造工具**——为一句修辞造一个工具，
是让判据牵着鼻子走。在文档里写明"对已有出处数字的对比与取整属合理用法"即可。

## 六、地雷清单（会真的浪费你时间的）

### 1. `pkill -f <关键词>` 会杀掉自己的 shell

Bash 工具的命令串里含该关键词时，`pkill -f` 会匹配到执行命令的 zsh 包装进程，
表现为命令以退出码 144 中断、后续步骤全部没跑。

```bash
# 错
pkill -f eval_regression; <后续命令>            # 后续不会执行

# 对
ps -eo pid,args --no-headers | grep -F "eval_regression" \
  | grep -v "grep\|zsh -c" | awk '{print $1}' | while read p; do kill -9 $p; done
```

同理 `pgrep -f <关键词>` 会自匹配，导致"进程还在"的误报。

### 2. `nohup ... &` 在后台工具里同样会被 SIGHUP 带走

八期又踩了一次：用 `run_in_background` 起 `nohup ... &`，日志 0 字节、
退出码却是 0（那是包装进程的退出码），而**真正的进程还活着**，
第二次重跑时两个进程一起抢 Qdrant 文件锁。
必须 `setsid ... > log 2>&1 < /dev/null & disown`，并且重跑前先按地雷 1 清干净。

### 3. Qdrant 本地嵌入模式是单进程文件锁

`uvicorn` 在跑时不能同时跑召回评测脚本（`data/qdrant` 被占）。
顺序是：停服务 → `rm -rf data/qdrant` → 跑评测 → 起服务。

### 4. 输出被管道缓冲，看不到进度

`uv run python ... | tail -N` 会让 Python 的 stdout 变块缓冲，跑完才有输出。
**十期又踩了一次**：`make eval 2>&1 | tail -45` 跑整轮，全程看不到任何进度，
而且 28 条的输出远超 45 行、前面的全丢了（报告文件不受影响，所以损失只是盲跑）。
长任务要看进度就别接 `tail`；实在想看，用产物做进度信号：

```bash
find data/conversations -name "*.jsonl" -newermt "HH:MM:SS" | wc -l   # 已跑完几条
```

长任务用 `setsid ... > log 2>&1 &` + `until grep -q <完成标志> log; do sleep N; done`
（用 `run_in_background: true`），并且加 `python -u`。

### 5. `hasattr` 在 AgentScope 的 dict 子类上会漏 KeyError

`ChatResponse` 继承 `DictMixin` → `dict`，属性查找走键查找，缺键抛 `KeyError`，
而 `hasattr` / `getattr(obj, name, default)` 只吞 `AttributeError`。
碰到这个类型别用属性反射。

### 6. 工具模块不能写 `from __future__ import annotations`

AgentScope 用 pydantic 从函数签名动态生成 JSON schema，字符串化注解会解析失败。
新增工具时注意。`app/application/harness/` 下的判定模块**可以**写（不进 schema 生成）。

### 7. 自建 OpenAI 兼容服务必须返回 `usage`

`rag.KnowledgeBase` 直接取 `usage.total_tokens`。缺了它商品索引一切正常、
品类知识库静默建库失败——同一服务喂两个消费者只挂一个，症状离故障点很远。

### 8. 评测脚本读 `os.environ`，必须先导入 settings 才有 `.env`

已修（导入 `app.infrastructure.settings` 触发 `load_dotenv`）。新写脚本时注意同样的坑。

### 9. AgentScope 的 `Msg` 只收关键字参数，且 content 必须是 block 列表

`Msg("main", text, "assistant")` 会抛 pydantic 校验错误。正确写法：
`Msg(name="main", content=[TextBlock(type="text", text=...)], role="assistant")`。
**更要命的是**：编排器有兜底 `except Exception`，这个错误会被吞成
`final_text = "[error] ..."`，于是"断言某事没发生"的测试全部平凡通过。
写编排器测试时必须加哨兵断言（见 `tests/test_orchestrator_provenance.py`）。

### 10. 落盘顺序不等于发生顺序

`JsonFileConversationStore` 一轮结束后**先写两条 turn、再批量写 events**，
所以文件里工具返回永远排在回复之后。按行顺序"边读边判"会让出处集合恒为空，
指标恒为 100%——而这个错误的读数看上去和真实读数一样像模像样。
读流水做指标前，先整份读完再判（`scripts/eval/trace_audit.py` 已按此实现）。

## 七、工作方法上的经验

**1. 评测跑的链路必须和线上跑的链路是同一条。**
七期自查发现 BM25 索引只在 `scripts/eval/*` 里构造、从没接进 `composition.py`——
评测选出的最优配置根本没上线，而且因为混合召回是"缺省 None 即退回原行为"的
加法式实现，"忘了接线"和"故意关掉"外观完全一样，没有任何告警。
新增可选依赖时，给它配一条启动期的显式声明**和一条钉住接线的测试**。

**2. 落盘的轨迹必须和喂给模型的返回是同一份。**
这是第 1 条的孪生问题，错在观测侧。八期首次扫描报出 13.4% 无出处金额，
逐条核对发现其中一半是假的——`tool.result` 事件是手挑字段拼的，
`filtered_out` / `insights` 后来加进返回值时没人记得同步事件。
**先怀疑观测，再怀疑被观测者。**

**3. 单次评测分不清"修好了"和"这回没触发"。**
加严 rubric 后重跑 `compare-two` 得 PASS，读判词才发现这次 Agent 根本没给组合总价，
新判据压根没被检验到。八期的修法是把用例改成**定向探测**——
query 明确索要组合总价，让待测行为每轮都发生。**能被跳过的判据等于没有判据。**
验收同理：memory-recall 修完连跑三次并逐条读判词，不是跑一次看绿。

**4. 交接文档自己也会过期，"顺手就能做"的那种最危险。**
八期结尾写"下轮顺手扫一次，成本为零（扫的是已经落盘的流水）"。
九期照做，拿回来一个一模一样的 6.7%——修复比流水晚两分钟，
已落盘的轨迹里压根没有那个新字段。写文档的人当时清楚修复刚落地，
但没意识到"已经落盘的流水"正是修复之前的产物。
**接手时遇到任何"零成本就能拿到新读数"的说法，先核对产物时间戳与代码 mtime**——
一次 `ls -l --time-style='+%m-%d %H:%M'` 比一次重扫便宜得多，
比一次白跑的整轮便宜几个数量级。

**5. 判据只能写 judge 判得了的事。**
judge 看到的是 transcript + ground_truth，**看不到工具调用与返回**。
十期给 `de-minimis-boundary-eu` 写了一条 P0「该数值必须来自工具返回」，
判词回来是"对话记录中未显示工具返回…按拿不准按不通过处理"——
Agent 那个 1170 明明是工具给的（轨迹里 `de_minimis_threshold_major: 1170.0` 白纸黑字），
**判据本身写错了位置**。正确的拆法是各归其位：
数值对不对 → 判据写死具体数字，judge 拿 ground_truth 核对；
有没有出处 → 交给金额出处校验，它扫轨迹，是确定性的。
顺带一条：judge 手上没有规则表时，它对到手价**只能验自洽、验不了正确**
（实测放过了"1,199 × 12% ≈ ¥3.48"这种基数写错、结果碰巧对的推导）。
十期把关税费率、免税额度、运费公式补进了 `build_ground_truth()`。

**6. "修了但读数没变"，第一嫌疑人是观测链路，第二才是代码。**
这是第 2 条在部署维度的同一条。九期照着交接文档去查"还有第三条没覆盖的代码路径"，
查了半天代码是对的——真相是被测服务比修复早启动 6 分钟，进程里跑的是旧代码。
**核对产物时间戳时，除了流水 mtime 与代码 mtime，还要核服务进程的启动时刻**
（`ps -eo pid,lstart`）。现在这条已经变成判据了（`/health` 的 `code.stale`
+ 开跑前拦截），但同型问题会换个地方再来：任何"跑起来之后就不再重读"的东西
——已加载的模块、缓存的配置、建好的索引——都有这个毛病。

**7. 写在文档里的纪律迟早会被绕开，能编码进判据的就别只写文档。**
"无出处金额率只在同一轮内横向比较"这句话八期就写在交接文档里了，
而门禁恰恰是拿绝对值比阈值的，扫的又是只增不减的累积目录——
纪律与判据当场打架，红灯来得毫无悬念。修法不是调阈值（那是让门禁慢性死亡），
是把比较口径编码进判据本身（`--report latest` 收敛到本轮）。
**下次写下"注意只能在 X 条件下比较"时，先问一句：这个条件能不能写进代码。**

**8. 一条新用例的价值，看它挖出了什么。**
15 条新用例里，`de-minimis-boundary-eu` 首跑 FAIL 0.325，读判词挖出的是
Agent 拿不到欧盟到手价、转而凭自身知识作答——而根因在工具侧
（目的国语义 + 参数描述诱导），不在 Agent。修完同一条用例 0.325 → 0.492，
P0 的到手价那条从 FAIL 转 PASS。
**扩用例集不是为了让分数好看，是为了让缺陷有地方冒出来。**
所以新用例首跑 FAIL 是预期结果，要做的是逐条读判词分清三件事：
Agent 真错了 / 判据写错了 / judge 判不了——这一条用例三样都占了。

**9. 一个错的解释比没有解释更坏。**
金额出处校验会给无出处金额推断成因（"疑似 A + B"）。容差按 1% 放宽时，
它会把 1619.9 认成 1625.9 的成因——看起来言之凿凿，实际把人引向错误的根因。
收紧到 ±1 绝对容差后，凑不出来的就老实标 `unsourced`。
诊断类输出宁可少说，不可说错。
