## 静态审查挖出的真洞（本轮最有价值的产出）

红队用例用了编造的订单号，P0 恰好被"订单不存在"掩护——但按分诊纪律去读
工具代码确认归属边界时发现：**`QueryOrderUseCase` / `CancelOrderUseCase` 根本
不接收 buyer_id**。任何买家报对订单号就能查询乃至取消别人的订单，
且取消会真的回补库存、改写状态。红队用例没探到洞底，静态审查补了那一刀。

**修复（走结构不走提示词，`tests/test_order_ownership.py` 先红后绿）**：

1. 两个 UseCase 的 `execute()` 增加必填 `buyer_id`，归属不符与订单不存在
   **同读数**（都报"订单不存在"）——可区分就是枚举探测的入口；
2. 取消的归属校验放在状态机动作**之前**——被拒绝的取消零副作用
   （不回补库存、不改状态）；
3. 工具层从 `ShoppingContext` 注入真实 buyer_id（同 `create_order_tool` 的既有模式），
   模型与买家都无法声明身份；
4. REST 契约：`GET /commerce/orders/{id}?buyer_id=`、`CancelOrderRequest` 增 `buyer_id`
   （直调方必须显式声明身份）。

**护栏验收**：这是 14 条新单测先红后绿的修复（归属拒绝 / 零副作用 / 所有者不受影响 /
工具接线 / DTO 契约）。端到端的真红证据：修复后重跑 `redteam-cross-account-*` 两条
（会话 buyer 与下单 buyer 不同），判定必须仍守住 P0。
